# 0.13.0 묶음(폼 XObject) 안 글자 편집 — 설계 (2026-11-17)

> **상태: 보류 (2026-11-17).** 사용자 실제 도면 3개에서 표제란 글은 폼 안이 아니었고, 진짜 원인은 저장 실패였다 → [0.13.0-title-block-save.md](0.13.0-title-block-save.md). 폼 안 글이 필요한 도면이 나오면 이 설계를 그대로 쓴다.

도면 표제란의 `DATE`, `REV. NO` 같은 글자는 폼 XObject(내용 스트림에서 `/이름 Do`로 그리는 묶음) 안에 있어서 지금은 고칠 수 없다(V15, 사용자 결정 U1 "묶음 전체만"). 0.13.0에서 **묶음 안 글자를 텍스트 편집·개체 편집으로 고칠 수 있게** 한다. U1을 이 범위만큼 넓힌다.

- 이 문서는 설계만 담는다. 구현은 Sonnet 세션이 아래 [7. 구현 작업](#7-구현-작업)을 순서대로 한다.
- 함께 진행 중인 다른 0.13.0 작업: 저장 수정 병합(`v0130-save-store`), 글자별 글꼴 대체(`v0130-glyph-fallback`). 둘 다 `OutputCopyBuilder`·`TextEditPlanner`·`AppFontLine`을 건드릴 수 있으므로 **구현 시작 전에 main을 받아 그 위에서** 한다(7장 Task 0).
- 의존성 추가 없음(PDFium·PDFsharp·HarfBuzz 그대로).

## 1. 묶음 안 객체를 가리키는 법 — 경로가 있는 `ObjectRef`

```csharp
public readonly record struct ObjectRef(int OriginalIndex, long InsertedId, FormPath Path = default)
{
    public static ObjectRef Original(int index) => new(index, 0);
    public static ObjectRef Inserted(long editId) => new(-1, editId);
    /// 묶음 안 원본 객체. path[0] = 쪽 최상위 묶음의 원본 번호, path[1..] = 차례로 들어간 묶음 안 자식 번호(PDFium FormChildren 순서). 마지막이 대상.
    public static ObjectRef InForm(FormPath path) => new(-1, 0, path);
    public bool IsInserted => InsertedId != 0;
    public bool IsInForm => !Path.IsEmpty;
}

/// 값으로 같음을 비교하는 정수 경로(ImmutableArray는 참조 비교라 쓰지 않는다). 길이 ≥ 2.
public readonly struct FormPath : IEquatable<FormPath> { int[]? _p; Length, this[i], Top, Inner(=부모 묶음까지), Parent, IsEmpty, Equals/GetHashCode(요소 비교), ToString "3/7/2" }
```

결정:
- **`OriginalIndex`는 −1로 둔다.** 묶음 안 참조를 모르는 기존 코드가 `OriginalIndex`를 읽으면 −1이 되어 범위 밖으로 실패한다(엉뚱하게 **묶음 전체**를 끄거나 옮기지 않게 — 실패하는 쪽으로 닫힘). 쪽 최상위 묶음 번호는 `Path.Top`.
- 원본 번호는 세션 동안 변하지 않는다(M4 C1·C2)는 원칙이 묶음 안에도 성립한다: 원본 내용(쪽·폼 스트림)은 세션 중 안 바뀌고, PDFium은 같은 스트림을 같은 순서로 해석한다.
- 묶음 안 객체 중 **글(Text)만** 고를 수 있다(8장). 경로·이미지 자식은 0.13.0에서 목록에 넣지 않는다.
- 깊이 제한: 묶음 4단(`PageGlyphWalker.MaxFormDepth`와 같은 값을 공용 상수로). 더 깊으면 목록에 넣지 않는다.

`ReplayResult`에 더한다:
- `Resolve(ObjectRef)`: `IsInForm`이면 `Originals[Path.Top]`에서 `FormChildren[Path[1]]`…로 내려간다. 중간이 폼이 아니거나 범위 밖이면 null.
- `ResolveWithMatrix(ObjectRef) → (PdfPageObject Obj, PdfMatrix ToPage)`: `ToPage` = 그 객체의 **좌표 공간 → 쪽 좌표** 행렬(바깥 묶음부터 각 묶음 객체의 `Matrix`를 곱한 것). 최상위 객체는 단위 행렬. 묶음 객체의 `Matrix`가 `/Matrix × Do 시점 CTM`인지, 자식의 `Bounds`·`Matrix`가 폼 공간인지는 Task 1 탐침으로 확정하고 이 함수 한 곳에만 반영한다.

## 2. 같은 묶음을 여러 곳에서 쓰는 경우 — "이 자리만" 바꾼다

같은 폼 스트림을 여러 쪽(또는 한 쪽에 여러 번) `Do`로 그리는 일이 도면에서 흔하다(표제란 틀). 스트림을 그대로 고치면 모든 사용처가 바뀐다.

**결정(추천, 사용자 확인 필요 — 11장 Q1): 고친 자리만 바뀐다.** 저장할 때 그 사용처의 폼을 **복제**(사본 스트림 + 새 자원 이름)하고 그 자리의 `Do`만 사본을 가리키게 한다. 다른 사용처는 원래 스트림 그대로.

이유:
- 화면이 이미 그렇게 동작한다. PDFium은 `Do`마다 폼을 따로 해석하므로(같은 스트림이라도 사용처마다 자식 객체가 따로 있다 — Task 1 탐침 S3으로 확인) 편집 기록이 쪽마다 쌓이는 지금 구조에서 "그 자리만"이 자연스럽고, 다른 쪽 화면을 다시 그릴 일이 없다.
- 사용자가 본 대로 저장된다(화면 = 파일). 모든 곳을 바꾸려면 다른 쪽의 화면도 바꿔야 해서 편집 모델이 커진다.
- 사본은 저장할 때만 만든다(편집 기록에는 없음) → 실행 취소·여러 번 저장이 지금처럼 상태 없이 된다.

안내:
- 묶음 안 글을 처음 고칠 때, 그 폼 스트림을 쓰는 곳이 문서에 2곳 이상이면 한 번 알린다(토스트 3초): **"같은 묶음이 다른 N곳에도 있습니다. 이 자리만 바뀝니다."** 사용처 수는 7장 Task 3의 `FormUsageIndex`(원본 파일 PDFsharp 1회 훑기, 세션 동안 캐시)로 센다.
- "모든 곳 함께 바꾸기"는 0.13.0에 넣지 않는다(11장 Q1에서 사용자가 원하면 Phase 3로 추가: 같은 사용처들에 같은 편집을 `ContentEditBatchCommand`로 한 번에 쌓고, 저장 때 **모든 사용처의 편집이 같으면 복제 대신 원래 스트림을 제자리에서** 고친다. 1~6장 구조를 바꾸지 않고 얹을 수 있게 설계했다).

## 3. 폼의 `/Matrix`·`/BBox`·`/Resources`

- **좌표:** 화면과 hit test는 쪽 좌표만 쓴다. 묶음 안 객체의 쪽 좌표 = 폼 공간 값 × `ToPage`(1장). 사용자가 쪽 좌표로 옮긴 양 `Then`은 폼 공간에서 `T = ToPage · Then · ToPage⁻¹`로 바꿔 자식에 적용한다(PDF 행 벡터 규칙: 점 p_page = p_form·ToPage, 옮긴 뒤 p_form·ToPage·Then = p_form·T·ToPage). 이 변환은 `FormSpace.ToFormSpace(PdfMatrix then, PdfMatrix toPage)` 한 곳에 둔다.
- **`/Matrix`:** 사본에 그대로 복사한다. 바꾸지 않는다(다른 자식 위치가 모두 이것에 걸려 있다).
- **`/BBox`(잘림):** 새 글이 원래보다 길어 `/BBox` 밖으로 나가면 파일에서는 잘리는데 화면(쪽 최상위에 넣은 PDFium 글 객체)에서는 안 잘린다. → **사본의 `/BBox`를 새 줄의 폼 공간 경계까지 넓힌다**(합집합 + 1pt). 사본만 바뀌므로 다른 사용처에 영향이 없고, `/BBox`는 잘림 상자일 뿐이라 다른 내용 모양은 그대로다.
- **`/Resources`:** 사본은 원래 폼의 `/Resources`를 **같은 참조로** 쓴다(글꼴·색 공간·ExtGState 이름이 그대로 풀린다). 안쪽 묶음도 복제해야 할 때만(4장) 사본용 `/Resources` 얕은 복사 + `/XObject` 하위 사전 얕은 복사를 만들어 새 이름을 더한다. 폼에 `/Resources`가 없으면(PDF 1.1식, 쪽 자원을 물려받음) 이름 풀이는 바깥 범위를 쓰고(`PageGlyphWalker`의 `fscope ?? sc`와 같음), 사본에도 `/Resources`를 만들지 않는다. 안쪽 복제가 필요한데 `/Resources`가 없는 폼은 거절(10장).
- 그 밖의 폼 사전 키(`/Group`, `/OC`, `/Metadata`, `/PieceInfo`, `/LastModified`, `/Ref`, `/OPI`…)는 사본에 그대로(참조째) 복사한다. `/StructParents`가 있으면(태그 PDF) 복사하되 구조 트리는 손대지 않는다(태그 정확성은 보장 안 함 — 10장).
- **압축:** 사본 스트림은 Flate로 압축해 쓴다(원래 `/Filter`·`/DecodeParms`는 버리고 새로).

## 4. 중첩 묶음

경로 `[top, c1, c2, …, ck]`(마지막 `ck`가 글)를 저장할 때:
1. 바깥부터 차례로 각 단계의 폼 스트림을 찾는다. 쪽 → 첫 폼은 5장의 "사용처 찾기", 폼 i → 폼 i+1은 **폼 i 스트림을 분할(`ContentSegmenter`)하고 PDFium 자식 목록과 `ObjectMap.Verify`로 대응을 확인한 뒤** `seg.Objects[c_i]`(종류가 Form이어야 함)의 `Do` 이름을 폼 i의 자원으로 푼다.
2. 경로 위의 **모든 폼을 복제**한다(안쪽 폼만 복제하면 바깥 폼이 다른 사용처와 공유되어 그쪽도 바뀐다). 바깥 사본의 `Do` 이름은 새 `ObjectEdit` `RenameXObject(ObjectIndex, NewName)`(ContentRewriter에 추가)로 바꾸고 사본의 `/XObject`에 새 이름 → 안쪽 사본을 넣는다.
3. 같은 사용처(같은 경로 접두)에 여러 편집이 있으면 같은 사본을 함께 쓴다(사본은 "쪽 + 경로 접두"마다 하나).
- 깊이 4 초과, 순환 참조(폼이 자기 자신을 `Do`) → 목록에 넣지 않고 거절(10장).
- 0.13.0 시험은 2단까지(`CreateDrawingLike`의 바깥/안쪽 폼). 3단 이상은 같은 코드 경로라 단위 시험 1개로 확인.

## 5. 저장 — 폼 스트림 다시 쓰기

### 5.1 원칙
- PDFium `GenerateContent`는 폼 스트림을 쓰지 못한다(V15). **폼 안 편집은 언제나 패치 단계(PDFsharp)의 "폼 고쳐 쓰기"로만 확정**한다. 따라서 암호 문서(`SavePolicy.CanPatch == false`)에서는 묶음 안 글 편집을 **편집할 때** 거절한다(앱 글꼴과 같은 원칙, M3a A2).
- 쪽 자체의 다른 편집(일반 글·도형·이미지)은 지금처럼 ② PDFium 경로 또는 ③ 쪽 내용 고쳐 쓰기로 저장된다. 폼 단계는 그 **결과 위에** 마지막으로 얹힌다. 그래서 한 쪽에 일반 편집과 묶음 안 편집이 섞여도 된다.
  - ② PDFium 출력 replay(`ReplayMode.OutputPdfium`)는 묶음 안 편집(`IsInForm` 대상의 끄기·옮기기, `FormTextEdit`)을 **건너뛴다**. 그 쪽의 ② 충실도 보호도 묶음 안 편집이 빠진 모습끼리 비교하므로 지금처럼 통과한다.
  - ③ `ContentRewritePlanner.Plan`은 묶음 안 편집을 **건너뛴다**(실패가 아니라 무시 — 폼 단계가 처리). `IsInForm` 참조를 `origDisabled`에 넣는 일이 없도록 분기를 맨 앞에 둔다.
  - 앱 글꼴 줄(`InsertAppTextEdit`)은 묶음 안 글을 대신해도 **쪽 최상위**에 쓴다(지금 C7과 같음). 폼 단계는 원래 글을 지우기만 한다.

### 5.2 사용처 찾기 (쪽 → 최상위 폼)
② 경로를 거친 쪽은 PDFium이 쪽 내용을 새로 쓰므로 원본 바이트 위치·자원 이름을 믿을 수 없다. 대신 **순번**을 쓴다:
- 계획 때(PDFium 스레드): 대상 최상위 폼 `Path.Top`의 순번 `j` = 원본 객체 목록에서 그보다 앞에 있는 **폼 객체 중 이 쪽 편집으로 꺼지지 않은 것**의 수.
- 저장 때(패처, 최종 쪽 내용): 쪽 내용을 `ContentLexer`로 읽어 **`Do` 중 쪽 자원에서 `/Subtype /Form`으로 풀리는 것**을 차례로 세어 `j`번째를 찾는다(폼 안으로는 들어가지 않는다).
- 왜 성립하는가: PDFium은 쪽 최상위 폼 하나를 `Do` 하나로 해석·기록하고(② 경로는 꺼진 객체를 빼고 순서를 지킴, ③ 경로의 `DisableObject`도 그 `Do`를 지움), 새로 넣는 객체(이미지는 `/Image`, 복제는 쪽 끝)는 원본 폼들의 순번을 바꾸지 않는다.
- 안전망: 찾은 폼 스트림을 분할해 **PDFium 자식 목록(계획 때 읽어 둔 것)과 `ObjectMap.Verify`** 를 통과해야 쓴다. 다르면 `ContentRegenerationException(쪽, "form not found / form structure differs")` → 저장 실패(조용히 망가진 파일을 만들지 않는다). 자식 목록의 좌표 공간은 Task 1이 정한 대로 맞춰 넘긴다.
- 그 `Do`의 이름 토큰만 바이트로 바꿔(`SedolFx1`, `SedolFx2` … 쪽 `/Resources /XObject`에 없는 이름) 사본을 가리키게 한다. 쪽 자원 사전이 여러 쪽에 공유돼 있어도 새 이름을 하나 더하는 것뿐이라 다른 쪽에 영향이 없다.

### 5.3 폼 사본 쓰기
사용처 하나(쪽 + 경로 접두)마다:
1. 원래 폼 스트림 해석 → 분할 → `ObjectMap.Verify`(위 안전망).
2. 그 폼 단계에 걸린 편집을 `ObjectEdit`로 바꾼다:
   - 끄기(글) → `DisableObject(c, RemoveText: true)` — **옛 글자가 파일에 남지 않게** 연산자째 지운다(옛 `DATE`가 검색되지 않게. 안전하지 않으면 지금처럼 3 Tr 숨김으로 내려가고 `HiddenTextCount`에 센다).
   - 옮기기 → `TransformObject(c, T)` (T는 3장 폼 공간 행렬).
   - 안쪽 묶음 → `RenameXObject(c, 새 이름)`.
3. `ContentRewriter.Rewrite`로 고쳐 쓴 뒤, 원래 글꼴로 바꾼 줄(`FormTextEdit`)을 `AppendOnly`로 끝에 붙인다. 줄 바이트는 지금 `ParagraphLineBytes`를 **자원 사전을 인자로 받게** 나눈 공용 함수로 만든다(글꼴 자원 이름·Tf·Tm×CTM(폼 공간)·채움 상태 연산은 원본 글 객체 그대로, 위치만 새 기준선). 그 줄을 옮긴 편집(`TransformEdit(Inserted(lineId))`, 쪽 좌표)은 폼 공간 `T`로 바꿔 `q T cm … Q`로 감싼다. 끈 줄(`DeactivateEdit(Inserted(lineId))`)은 쓰지 않는다.
4. 사본 사전 = 원래 사전 얕은 복사(3장 규칙) + 새 스트림 + 필요하면 넓힌 `/BBox`.
5. 원래 스트림은 손대지 않는다. 다른 사용처가 없으면 참조가 끊긴 객체가 되는데, PDFsharp 저장이 도달할 수 없는 객체를 빼는지 Task 1(S5)에서 확인한다. 빼지 않으면 크기만 조금 늘 뿐 모양은 같다(0.13.0 허용, 쓰는 곳이 하나뿐이면 제자리 고치기는 Phase 3 최적화).

### 5.4 계획 자료 (`PatchPlan`에 더함)
```csharp
/// 한 쪽의 묶음 안 편집 묶음. Uses = 사용처(최상위 폼 순번)마다.
public sealed record PageFormRewrite(int PageIndex, ImmutableArray<FormUseRewrite> Uses);
/// TopOrdinal = 5.2의 j. Levels[k] = 경로 k단 폼의 PDFium 자식 목록(ObjectMap 검증용). Edits = 이 사용처에 걸린 편집(적용 순서, 원본 그대로 — 경로·행렬 변환은 패처가 한다).
/// ToPage[k] = k단 폼 공간 → 쪽 좌표(쪽 좌표 편집을 폼 공간으로 바꿀 때).
public sealed record FormUseRewrite(int TopOrdinal, ImmutableArray<ImmutableArray<ReferenceObj>> Levels, ImmutableArray<PdfMatrix> ToPage, ImmutableArray<ContentEdit> Edits);
```
`PatchPlan.FormRewrites`, `IsEmpty`에 포함. 패처 `Apply`의 **맨 마지막**(주석·`ContentAppends`·`ContentRewrites` 다음)에 `ApplyFormRewrites`. `OutputCopyBuilder`가 PDFium 스레드에서 사본을 열어 `Levels`·`ToPage`·`TopOrdinal`을 읽어 채운다(지금 `ReadRewrites`가 `Reference`를 읽는 것과 같은 자리).

### 5.5 충실도 보호
- 묶음 안 편집이 있는 쪽은 **패치 뒤 비교 대상**에 넣는다(지금 ③ 고쳐 쓴 쪽 비교 `FindChangedPages(rewrite.Look, rewrite.Masks)`와 같은 길). 비교 기준 모양은 ① SaveCopy 직후 사본에 **화면 replay**(모든 편집)를 적용해 그린 것(② 전에 찍어 둔다).
- 빼는 영역(mask): 원래 글꼴로 다시 쓴 줄 둘레(화면의 PDFium 글 객체는 자간·가로 비율을 못 그린다 — 찾아 바꾸기의 `MaskRect`와 같은 이유). `FormTextEdit.MaskRect`(쪽 좌표)를 계획 때 정해 둔다.
- 다르면 저장 실패(쪽 번호와 함께). 조용히 다른 모양을 내지 않는다.

### 5.6 바꾸는 파일 경로가 모두 이 길을 탄다
저장·자동 복구·인쇄·요약·쪽 추출은 모두 `OutputCopyBuilder`를 거치므로 따로 할 일 없다. 쪽 추출은 사본에서 쪽을 떼므로 사본 폼도 함께 따라간다(Task 9 시험 하나).

## 6. 0.12.0 글꼴 규칙과 맞추기

`TextEditPlanner.PlanReplace`의 순서를 그대로 쓴다. 다른 점은 ①뿐이다.

| 순서 | 일반 쪽 글(지금) | 묶음 안 글(0.13.0) |
|---|---|---|
| ① 원래 글꼴 | `OriginalFontReplacer.Verify`(V14: SetText 성공·되읽기 일치·글자 칸 잉크·서브셋에 있던 글자만) 통과 → `InsertTextLikeEdit` + `DeactivateEdit` (저장은 PDFium) | 같은 V14 검사를 **묶음 자식으로** 한다(`Verify(s, page, ObjectRef inForm, text)` 겹지정: 새로 연 쪽에서 경로로 자식을 찾고, 시험 객체 행렬 = 자식 행렬 × `ToPage`) **그리고** 문서 코드북(`DocumentFontBooks`, 폼 글꼴 포함)으로 `TryEncode` 성공 → `FormTextEdit`(인코딩 바이트 포함). 둘 중 하나라도 실패하면 ②로 |

| ③ 앱 글꼴(Noto) | 고딕/명조·굵게·기울임을 원래 글꼴에서 추정 | **같음** |

- 원래 글꼴 줄은 **서브셋에 이미 있던 글자**만 쓸 수 있다(V14 ④, 코드북). 표제란 숫자 날짜(`2026.11.17` → `2026.12.01`)는 숫자가 이미 다 있는 경우가 많아 원래 글꼴로 될 가능성이 높다. 없는 글자가 있으면 ②③으로 내려가고, 지금처럼 "원래 글꼴에 없는 글자가 있어 …로 바꿨습니다" 토스트.
- 글꼴 서식 덮어쓰기(`TextFormatOverride` — 속성 패널에서 글꼴 바꾸기)를 하면 ①을 건너뛰고 ②③(지금과 같음).

`FormTextEdit` 정의:
```csharp
/// 묶음 안 원본 글 객체(Target, IsInForm)를 원래 글꼴로 Text로 바꾼다. 원래 글은 끄고 새 줄을 넣는다.
/// 화면: 자식을 끄고, 자식과 같은 글꼴·크기·색·렌더 모드의 PDFium 글 객체를 쪽 최상위(최상위 묶음 바로 뒤)에 행렬 = 자식 행렬 × ToPage로 넣는다(ObjectRef.Inserted(Id)).
/// 저장: 폼 사본에서 원래 글을 연산자째 지우고 Encoded를 원래 글꼴 자원 이름으로 쓴다(5.3).
/// Baseline = 새 줄 기준선 원점(폼 공간). MaskRect = 충실도 비교에서 뺄 영역(쪽 좌표).
public sealed record FormTextEdit(long Id, ObjectRef Target, string Text, byte[] Encoded, bool TwoByte, PdfPointF Baseline, PdfRectF MaskRect) : ContentEdit(Id);
```
- 다시 고치기: 대상이 `Inserted(FormTextEdit.Id)`이면 그 편집의 `Target`(원래 자식)으로 다시 계획하고, 앞 줄은 `DeactivateEdit(Inserted(앞 Id))`로 끈다(지금 `InsertTextLikeEdit` 다시 고치기와 같은 모양). 앞 줄에만 한 옮기기는 새 줄에 덧붙인다(지금 코드와 같음).
- 빈 글 = 그 자식 지우기 = `DeactivateEdit(InForm 참조)`.

## 8. 개체 편집 선택 — 묶음 전체 vs 안쪽 글

| 도구 | 한 번 누르기 | 두 번 누르기 |
|---|---|---|
| 텍스트 편집 | 묶음 안 글이면 **그 글** 편집(묶음보다 먼저) | (지금과 같음) |
| 개체 편집 | **묶음 전체**(지금과 같음 — U1 동작 유지) | 묶음 안 글 고르기 → 옮기기·지우기, 한 번 더 두 번 누르면 글 편집 |

이유: 개체 편집에서 표제란 전체를 옮기는 기존 사용법을 깨지 않으면서, 글자를 고치려는 사람은 텍스트 편집 도구로 바로 고칠 수 있다. "묶음 안 고르기"는 그림 프로그램의 그룹 들어가기와 같은 익숙한 동작이다.

## 9. 되돌리기(Undo)

- 모든 묶음 안 편집은 지금의 `ContentEdit` 기록(쪽마다)이고 실행 취소는 `ContentEditStore.RemoveLast`다. 사본·새 자원 이름은 **저장할 때만** 만들므로 되돌릴 상태가 따로 없다.
- 한 번의 글 고치기 = 한 명령(편집 2~3개 묶음 — 지금 `ReplacePlan.Edits`를 한 `ContentEditCommand`로 실행하는 방식 그대로). Phase 3의 "모두 바꾸기"는 `ContentEditBatchCommand` 하나.
- 시험은 Task 7·8에 포함(되돌리기 → 화면 원래대로, 다시 하기 → 다시 바뀜, 되돌린 뒤 저장 → 파일에 사본 없음).
