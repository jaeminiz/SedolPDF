# 0.14.0 저장 속도 — 측정·원인·설계

작성: 2026-11-19 · 범위: 측정과 설계만 (구현은 별도 세션)

## 1. 한 줄 요약

큰 도면을 저장할 때 시간의 **약 80%는 "쪽 내용 고치기 검사"(`RepairContent`)** 가 씁니다.
이 검사는 0.8.0 이전 저장이 남긴 깨진 쪽을 찾으려고, 수정하지 않은 쪽까지 **모든 쪽의 내용 스트림을 매번 세 번씩 해석**합니다.
그다음은 PDFium으로 모든 쪽을 불러 주석 수를 세는 두 단계(약 1.6초)입니다.
처음에 의심했던 렌더 비교, PDFium `GenerateContent`, PDFsharp 다시 쓰기, `ObjectMap.Verify`는 모두 0.1초 안팎이라 원인이 아닙니다.

## 2. 실제 저장 경로 (코드로 확인함)

`FileWorkflow.TrySaveAsync` → `SaveService.SaveAsync` → `OutputCopyBuilder.BuildAsync`

| # | 단계 | 코드 | 언제 |
|---|---|---|---|
| 1 | 주석 Flush + 패치 계획 | `DocumentSession.FlushIfNeeded` | 항상 |
| 2 | PDFium 전체 저장(임시 파일) | `PdfDocument.SaveCopy` | 항상 |
| 3 | 쪽별 주석 수 세기(살아 있는 문서, **모든 쪽 `LoadPage`**) | `OutputCopyBuilder.CollectAnnotCounts` | 항상 |
| 4 | 객체 편집 확정: 시험 적용(PDFsharp) · PDFium `GenerateContent` · 모양 확인(렌더 비교) | `RegenerateContent` | 객체 편집이 있을 때, **편집한 쪽만** |
| 5 | PDFsharp 패치(열기 → 고치기 → 전체 저장) | `PdfSharpAnnotationPatcher.Apply` | 패치 계획이 있을 때 |
| 6 | 고쳐 쓴 쪽 모양 확인 | `FindChangedPages` | 내용 고쳐 쓰기가 있을 때, 그 쪽만 |
| 7 | **쪽 내용 고치기 검사 — 모든 쪽 해석** | `PdfSharpAnnotationPatcher.RepairContent` → `ContentRepair.RepairStreams` | **항상**(암호 없는 문서) |
| 8 | 다시 열어 검증(**모든 쪽 `LoadPage`** 후 주석 수 비교) | `SaveService` ③ | 항상 |
| 9 | 글꼴 출처 보관(파일 복사) | `RetainFontSource` | 편집이 있을 때 |
| 10 | 파일 교체 | `File.Replace` | 항상 |
| 11 | SHA-256(저장한 파일 다시 읽기) | `SaveService` | 항상 |

`ObjectMap.Verify`는 4·5단계 안에서 편집한 쪽에만 돕니다.

### 7단계를 더 나누면 (큰 도면, 2회 같은 값)

| 항목 | ms |
|---|---:|
| PDFsharp 열기 | 57~129 |
| 내용 스트림 풀기(`LoadStreams`) | 76~84 |
| 스트림마다 한 번 해석(`ContentLexer.Parse`) | 2,213~2,284 |
| `RepairStreams` 전체 | 6,931~6,954 |
| 참고: 합친 내용 한 번 해석 | ~2,340 |
| 참고: `RemoveDanglingFragments`(안에서 다시 해석) | ~2,390 |
| 참고: `RemoveUnmatchedRestores`(안에서 다시 해석) | ~2,430 |

`RepairStreams`는 쪽마다 ① 스트림별 해석 ② `RemoveDanglingFragments`의 합친 내용 해석 ③ `RemoveUnmatchedRestores`의 해석 — **같은 내용을 세 번 해석**합니다. 한 번에 약 2.3초 × 3 ≈ 7초.
75쪽 중 34쪽이 스트림이 여러 개, 전체 313개 스트림. 이 파일은 고칠 쪽이 하나도 없었습니다(검사만 하고 결과는 "깨끗함").

## 4. 원인 순위

| 순위 | 원인 | 큰 도면에서 | 비율 |
|---|---|---:|---:|
| 1 | 쪽 내용 고치기 검사가 **수정 여부와 관계없이 모든 쪽**을 **매번 세 번** 해석 | ~7.5초 | ~80% |
| 2 | 다시 열어 검증: 모든 쪽 PDFium `LoadPage`(쪽 내용 전체 해석) | ~0.85초 | ~9% |
| 3 | 저장 전 주석 수 세기: 모든 쪽 PDFium `LoadPage` | ~0.8초 | ~8% |
| 4 | PDFsharp 패치 열기·저장(패치가 있을 때) | ~0.1초 | ~1% |
| 5 | 객체 편집 확정(시험 적용·GenerateContent·렌더 비교 합계) | ~0.1초 | ~1% |
| – | PDFium SaveCopy, SHA-256, 교체, ObjectMap.Verify | 각 0.06초 이하 | – |

PDF-XChange가 빠른 이유: 증분 저장과 별개로, 이런 "전체 쪽 검사"를 저장마다 하지 않기 때문입니다. 1~3번만 없애도 우리 저장은 0.3초 안팎이 됩니다(5절 계산). 그래서 **증분 저장은 이번 버전에 필요 없습니다.**

## 5. 개선안

### 안 A. 고치기 검사 결과를 "내용 지문"으로 기억하고, 문서를 열 때 미리 검사 (권장, 1순위)

- 내용: 쪽의 내용 스트림 목록(스트림 경계 포함)의 지문(예: 스트림마다 길이 + SHA-256을 이어 붙여 다시 해시)을 키로, "깨끗함" 결과를 프로세스 안 캐시(`ConcurrentDictionary`)에 둡니다.
  - 문서를 연 뒤 백그라운드(낮은 우선순위, 첫 화면을 그린 뒤, 문서를 닫으면 취소)에서 원본 바이트로 모든 쪽을 검사해 깨끗한 쪽의 지문을 채웁니다. `LoadOriginalsAsync`처럼 이미 원본 바이트가 메모리에 있습니다.
  - 저장 때 `RepairContent`는 쪽마다 스트림을 풀고(전체 ~80ms) 지문을 구해, 캐시에 "깨끗함"이 있으면 해석을 건너뜁니다. 없거나 깨끗하지 않으면 지금과 **똑같이** `RepairStreams`를 돌립니다.
  - 저장 때 검사해서 깨끗했던 쪽도 캐시에 넣습니다(다음 저장부터 빠름).
  - 미리 검사가 아직 안 끝났으면 저장은 지금처럼 그냥 검사합니다(더 느려지지 않음).
- 왜 안전한가: 판단 규칙(`RepairStreams`)은 바꾸지 않습니다. "같은 바이트·같은 스트림 경계 → 같은 결과"라는 사실만 씁니다. 쪽 번호·PageId에 의존하지 않으므로 쪽 넣기·지우기·순서 바꾸기·다른 파일에서 가져온 쪽에도 맞습니다(새 내용이면 지문이 달라서 그냥 검사).
- 예상 이득: 7단계 7.5초 → 약 0.1~0.15초(PDFsharp 열기 + 풀기 + 해시). **큰 도면 저장 9.3초 → 약 1.9초**(안 C까지 하면 약 0.3초).
- 위험
  - 저장 정확성: 지문 충돌 — SHA-256이라 사실상 없음. 스트림 경계를 키에 넣지 않으면 규칙이 다른 결과를 낼 수 있음 → **경계를 반드시 키에 넣음**.
  - 서식 보존: 고치는 규칙 자체는 그대로이므로 표제란·칸 간격 영향 없음.
  - 자원: 백그라운드 검사가 CPU를 7초가량 씀(안 B와 같이 하면 1~2초). 열자마자 저장하면 그 차이만큼 느림.
  - 메모리: 쪽마다 32바이트 + 길이 목록, 무시할 만함.
- 시험
  - 단위: 같은 내용 → 캐시 적중, 1바이트 다름 → 다시 검사, 스트림 경계만 다름 → 다시 검사.
  - 회귀: `DamagedContentPdfFactory`의 깨진 쪽, `ContentRepairSaveTests` 전부 통과(깨진 쪽은 캐시에 "깨끗함"으로 들어가지 않으므로 계속 고쳐야 함).
  - 같은 결과: 캐시를 켜고 끈 두 저장 결과 파일의 바이트가 같음(합성 시료 + 실제 도면).
  - 속도: `SaveSpeedBenchTests`로 7단계가 200ms 아래인지 확인.

### 안 B. 고치기 검사 자체를 빠르게: 한 번만 해석 + 쪽 병렬 (권장, 2순위)

- 내용
  - `RepairStreams` 안에서 스트림별 해석 결과를 이어 붙여(오프셋 보정) 합친 내용의 연산자 목록을 만들고, `RemoveDanglingFragments`·`RemoveUnmatchedRestores`가 그 목록을 받아 쓰게 합니다(해석 3회 → 1회). 고칠 것이 없는 쪽은 합친 바이트도 만들 필요가 없습니다.
  - 풀기(PDFsharp, 스레드 안전 아님)는 순서대로, 해석·판단(순수 관리 코드)은 `Parallel.For`로 쪽마다 나눠 돌립니다. 결과 적용(스트림 바꾸기)은 다시 순서대로.
- 예상 이득: 해석 3회 → 1회로 약 7초 → 2.3초, 8코어 병렬로 → 약 0.4~0.6초. 안 A의 첫 검사(열 때 미리 검사, 또는 미리 검사가 끝나기 전 저장)를 빠르게 합니다.
- 위험
  - 저장 정확성: 연산자 위치(오프셋)를 잘못 보정하면 잘못된 곳을 지움 → 결과가 지금 구현과 **바이트 단위로 같음**을 시험으로 강제.
  - 경계 조건: 스트림 하나가 해석에 실패하면 지금은 `RemoveUnmatchedRestores(Join(...))`로 내려감 — 이 길은 그대로 둠.
  - 병렬: 쪽끼리 공유 상태 없음. 예외는 쪽 단위로 모아 지금과 같은 순서로 처리.
- 시험
  - 기존 구현을 시험 쪽에 "기준 구현"으로 복사해 두고, 합성 깨진 시료 + `private/` PDF + 실제 도면의 모든 쪽에서 새/옛 결과 바이트가 같은지 비교(실제 도면은 환경 변수 있을 때만).
  - `ContentRepair` 단위 시험 전부 통과.

### 안 C. 주석 수 세기와 검증에서 "모든 쪽 LoadPage"를 없애기 (권장, 3순위)

- 내용
  - 3단계(저장 전 주석 수): 살아 있는 문서의 모든 쪽을 불러 세지 않고, 바뀐 쪽(주석 변경·객체 편집·쪽 넣기/회전 등)만 PDFium으로 세고 나머지는 원본 파일의 `/Annots` 배열 길이를 씁니다. 또는 열 때 이미 세어 둔 값(`LoadOriginalsAsync`가 모든 쪽을 셈)을 모델에 남겨 씁니다.
  - 8단계(다시 열어 검증): PDFium으로 다시 열기 + 쪽 수 확인은 그대로(빠름). 쪽별 `LoadPage`는 바뀐 쪽 + 패치한 쪽 + 고친 쪽만. 나머지 쪽의 주석 수는 7단계에서 이미 연 PDFsharp 문서의 `/Annots` 길이로 비교.
- 예상 이득: 약 1.6초 → 0.1초 안팎.
- 위험
  - 검증이 약해짐: 지금은 "PDFium이 모든 쪽을 열 수 있다"까지 확인함. 바뀌지 않은 쪽은 바이트가 원본과 같으므로 위험은 낮지만 0은 아님(예: PDFsharp가 저장하며 쪽 트리·자원 참조를 망가뜨리는 경우). → 바뀌지 않은 쪽도 `FPDF_GetPageSizeByIndexF` 같은 가벼운 확인은 남김.
  - 수 세는 방법이 둘이 됨: PDFium `FPDFPage_GetAnnotCount`와 원시 `/Annots` 길이가 다른 파일이 있으면 거짓 실패 → 아래 시험으로 먼저 확인하고, 다르면 그 문서만 지금 방식으로.
- 시험
  - 모든 시료 + 실제 도면에서 PDFium 주석 수 == 원시 `/Annots` 길이(쪽마다)인지 먼저 확인하는 시험.
  - 일부러 패치가 주석을 빠뜨리게 한 경우 검증이 여전히 실패하는지(기존 검증 시험 유지).

### 안 D. 렌더 비교 생략·저해상도·백그라운드

- 측정 결과 렌더 비교(4d·6단계)는 편집한 쪽에만 돌고 큰 도면에서도 19ms입니다. 이미 640px 이하로 작게 그립니다.
- **하지 않음.** 이득이 거의 없고, 이것이 원래 글꼴 편집·칸 간격·색 공간 회귀를 잡는 안전장치입니다.

### 안 E. 증분 저장(incremental update)

- PDFium `FPDF_SaveAsCopy`의 `FPDF_INCREMENTAL`로 바뀐 객체만 뒤에 붙여 쓰는 방식.
- 이득: SaveCopy 50ms + PDFsharp 패치 열기·저장 ~100ms 정도. 안 A~C 뒤에는 남는 이득이 작습니다.
- 위험이 큼: PDFsharp 패치·고쳐 쓰기·고치기 검사가 모두 "전체 파일을 다시 쓰는" 전제로 짜여 있어 전부 바꿔야 함. 지운 원본 글이 이전 판(revision)에 남아 복원될 수 있음(보안·개인정보). 파일 크기가 저장할 때마다 커짐.
- **이번 버전에서는 하지 않음.** 안 A~C 뒤에도 느리다는 보고가 있으면 다시 봅니다.

### 안 F. 작은 정리 (선택)

- `PdfDocument.SaveCopy`의 `FileStream` 버퍼를 1MB로(지금 기본 4KB) — SaveCopy 50ms 중 일부.
- SHA-256: 저장한 파일을 다시 읽지 않고 교체 전 임시 파일 바이트로 계산(10ms).
- 이득이 작으므로 다른 일과 함께 할 때만.

## 6. 지켜야 할 것 (모든 안 공통)

- `RepairStreams`의 판단 규칙은 바꾸지 않는다. 바뀌는 것은 "언제·몇 번 해석하는가"뿐.
- 표제란 원래 글꼴 편집·칸 간격(`ColumnGapTests`, 0.13.0 표제란 시험), 색 공간 충실도(`ColorSpaceFidelityTests`), 깨진 쪽 고치기(`ContentRepairSaveTests`) 시험은 모두 그대로 통과해야 한다.
- 새 의존성 없음(SHA-256·`Parallel.For`는 .NET 기본).
- `SaveTrace`는 남겨 두고, 구현 뒤 같은 하네스로 다시 재서 이 문서 표를 고친다.

## 7. 구현 작업 목록 (Sonnet 세션용)

순서대로. 각 작업은 따로 커밋.

1. **고치기 검사 기준 시험 만들기** — 지금 `ContentRepair.RepairStreams`를 시험 프로젝트에 기준 구현으로 복사. 합성 깨진 시료(`DamagedContentPdfFactory`) + `private/`(있으면) + `SEDOL_BENCH_PDF`(있으면)의 모든 쪽에서 새 구현 결과 바이트 == 기준 결과인지 비교하는 시험. (안 B의 안전망)
2. **안 B-1: 해석 한 번만** — `RepairStreams`가 스트림별 해석 결과를 이어 붙인 연산자 목록을 만들어 `RemoveDanglingFragments`/`RemoveUnmatchedRestores`의 "이미 해석한 입력" 오버로드에 넘김. 공개 메서드 동작은 그대로. 1번 시험 통과.
3. **안 B-2: 쪽 병렬** — `PdfSharpAnnotationPatcher.RepairContent`에서 풀기는 순서대로, `RepairStreams`는 `Parallel.For`, 스트림 바꾸기는 순서대로. 결과 쪽 번호 순서 유지.
4. **안 A: 내용 지문 캐시** — `ContentRepairCache`(프로세스 전역, 스레드 안전): 키 = 스트림별 (길이, SHA-256) 목록의 해시. `RepairContent`가 적중 시 해석 생략, 깨끗하면 넣음. 단위 시험 3종(같음/1바이트 다름/경계만 다름).
5. **안 A: 열 때 미리 검사** — `DocumentSession` 연 뒤(첫 화면 뒤, 낮은 우선순위, 닫으면 취소) 원본 바이트로 PDFsharp를 열어 모든 쪽 지문·검사 결과를 캐시에 채움. 암호 문서는 건너뜀(지금도 고치기 검사를 안 함). 저장과 겹치면 저장 쪽이 그냥 검사(기다리지 않음).
6. **안 C 사전 확인 시험** — 시료 전부에서 PDFium 쪽별 주석 수 == 원시 `/Annots` 길이 확인. 다르면 7번 설계를 고친 뒤 진행(관제에 보고).
7. **안 C: 주석 수·검증 줄이기** — 3단계는 바뀐 쪽만 PDFium으로 세기, 8단계는 다시 열기 + 쪽 수 + 바뀐 쪽 `LoadPage` + 나머지는 원시 `/Annots`와 가벼운 쪽 크기 확인. "바뀐 쪽" 집합은 OutputCopyBuilder가 모아 `OutputCopy`로 넘김.
8. **다시 재기** — `SaveSpeedBenchTests`로 측정, 이 문서 5절 표 아래에 "구현 후" 표 추가. 전체 시험(`PdfEditor.sln`) 통과 확인.
9. (선택) 안 F.

완료 기준: 큰 도면(75쪽) 저장만·주석 1개·글 한 줄 모두 미리 검사 뒤 0.5초 이하, 미리 검사 전 1초 이하. 전체 시험 통과.

- 작업 1~2: 고치기 검사 해석 3회 → 1회(스트림별 결과를 이어 위치만 옮김). 기준 구현과 바이트 단위로 같음(합성 15종 + private/ PDF 전부 + 실제 도면 75쪽).
