# 0.15.0 그러데이션 쪽의 객체 편집 저장 — 진단과 설계 (2026-11-20)

배경: 0.14.0 출시판에서 사용자가 `3.GD5PRO.pdf`(조선 도면, 1쪽, 고객 파일 — 커밋 안 함) 1쪽의 객체를 편집하고 저장하자
① "모양이 조금 달라질 수 있습니다 … 그래도 저장하시겠습니까?" → ② [그래도 저장] → "… 저장하지 못했습니다. … 실행 취소한 뒤 저장해 주세요" 가 떴다. 저장이 아예 안 된다.

## 1. 진단

### 1.1 객체 편집마다 지금 저장 경로 (코드 확인)
`OutputCopyBuilder.RegenerateContent`:
1. 복제(`DuplicateObjectEdit`)가 있는 쪽은 처음부터 **내용 스트림 고쳐 쓰기**(M4x, `PdfSharpAnnotationPatcher.RewritePage`)로만 저장한다.
2. 그 밖의 쪽은 먼저 PDFium 다시 쓰기(`GenerateContent`) + 모양 검사. 그러데이션(sh·셰이딩 패턴)·무늬·이미지 마스크가 있으면 모양이 달라져 검사에 걸리고, 패치 가능한 문서면 그 쪽을 **고쳐 쓰기로 넘긴다**.
3. 고쳐 쓰기 계획(`ContentRewritePlanner.Plan`)과 바이트 고쳐 쓰기(`ContentRewriter.Rewrite`, `ObjectSnippet.Extract`):

| 편집 | 원본 객체 | 고쳐 쓰기 방법 | 지금 실패하는 경우 |
|---|---|---|---|
| 옮기기·크기 바꾸기 (`TransformEdit`) | 경로·그림·폼·셰이딩 | 객체 앞뒤 `q X cm … Q` (X = C·Then·C⁻¹) | 경로 안 W(클립), 경로 중간의 낯선 연산자 |
| 〃 | 글 | 원본을 `3 Tr`로 숨기고 ET 뒤에 `q X cm … BT Tm show ET Q` 사본 | **글 위치(Tm)를 모르거나 BT 안에 q/Q/cm** → `text not movable` |
| 지우기 (`DeactivateEdit`) | 경로 `n`, 그림·폼·셰이딩 연산자 삭제, 글 `3 Tr`(문단·한 줄 편집은 연산자째 삭제) | | 잘림 글(Tr ≥ 4) |
| 복제 (`DuplicateObjectEdit`) | 모두 | 쪽 끝에 `q then cm C cm 상태 연산자 … Q` 조각 | **글: 위 옮기기와 같은 조건** → `text not copyable`, 경로 안 W |
| 선·채움 색/굵기 (`SetShapeStyleEdit`) | 경로 | **없음** | 원본 도형이면 언제나 `needs the PDFium path` |
| 글자 색 (`SetTextColorEdit`) | 글 | 복제 사본만 됨 | 원본 글이면 언제나 `unsupported edit` |

즉 옮기기·크기·지우기·복제는 **이미 고쳐 쓰기로 저장된다**(그러데이션 쪽 포함, 시험 `ContentRewriteSaveTests`·`DuplicateSaveTests`). 막히는 것은 위 표의 굵은 칸이다.

### 1.3 왜 "경고 → 그래도 저장 → 실패"인가
- `FileWorkflow.TrySaveAsync`는 **모든** `ContentRegenerationException`을 "모양이 달라질 수 있음"으로 보고 묻는다.
- 그런데 이 예외는 두 가지 뜻으로 쓰인다: (가) 저장은 되지만 모양이 다를 수 있음(PDFium 결과·고쳐 쓰기 결과의 모양 검사 실패) (나) **고쳐 쓰기를 할 수 없음**(패처의 계획·해석·조각 실패).
- (나)에서 "그래도 저장"을 눌러도 `AcceptLookChanges`는 모양 검사만 건너뛸 뿐 고쳐 쓰기 실패는 그대로라 같은 예외가 다시 난다. 복제 쪽은 PDFium 대안도 없다.

## 2. 목표
1. 그러데이션·무늬·이미지 마스크 쪽에서 옮기기·크기 바꾸기·지우기·복제·선/채움 스타일·글자 색 편집이 **묻지 않고 저장**된다(저장 모양 = 화면 모양, 다시 열어도 편집 유지).
2. 고쳐 쓰기가 정말 불가능한 경우만 남긴다. 그때는 **처음부터 원인을 알려 주는 안내 한 번**(경고 뒤 실패 흐름 없음).
   - 대안(PDFium 결과)이 있는 쪽: "모양이 달라질 수 있음 — 그래도 저장?" 한 번 → 예면 **반드시 저장된다**.
   - 대안이 없는 쪽(복제 등): 묻지 않고 원인 안내 한 번(저장 안 함).

## 3. 설계 A — BT 안 위치를 모르는 글도 복제·옮기기 (사용자 사유의 직접 수정)

### 3.1 방법: "BT 머리 다시 보내기"(prefix replay)
글 사본을 만들 때 Tm을 미리 알 필요 없이, **그 글의 BT부터 그 글까지의 글 위치·글 상태 연산자를 그대로 다시 보낸다.** 앞선 글 보이기는 `3 Tr`(보이지 않음)로 보내 글자 이동량만 반영한다. 글 공간의 Tm은 CTM과 무관하게 쌓이므로 BT 안의 `q`/`Q`/`cm`은 빼고, 사본의 CTM은 그 글을 그리던 시점의 CTM(`obj.Ctm`)으로 맞춘다.

사본(`then` = 쪽 공간 변환, `open` = 지금처럼 `q … cm`):
```
q <open> <BT 시점 글 상태: Tf(BT 시점) Tc Tw Tz TL Ts> 3 Tr
BT
  <BtOp+1 … OpIndex-1 중: Tf Tc Tw Tz TL Ts Tm Td TD T* 그대로, Tj/TJ/'/" 는 그대로(3 Tr 상태라 안 보임), 그 밖(q Q cm Tr 색·gs 등)은 뺌>
  <그 글 시점 상태 연산자 ReplayOps(색·gs·선 굵기)> [<색 덮어쓰기>] <그 글 시점 Tf> <s.Tr> Tr
  <그 글의 보이기 연산자 그대로>
ET Q
```
- `'`·`"`(줄 바꿈 보이기)도 앞 글이면 그대로(이동 포함), 대상 글이면 지금처럼 보이기만(줄 바꿈은 머리에서 이미 반영되지 않으므로 대상 글이 `'`/`"`면 그 줄 바꿈 효과 `T*`를 앞에 넣는다 — `"`는 Tw·Tc도).
- 필요한 새 정보(`ContentSegmenter`):
  - `TextSnapshot.BtState` = BT를 만난 순간의 (Tc, Tw, Tz, TL, Ts, FontOp). `BT` 처리에서 기록.
  - `TextSnapshot.EtCtm` = 짝 ET 시점의 CTM(BT 안 cm/q/Q 때문에 그 글의 CTM과 다를 수 있음). `ET` 처리에서 채움.
  - `TextSnapshot.TmKnown`(지금 `Movable` 계산의 `tmKnown`) — 지금 방법(Tm 직접)과 새 방법을 고르는 데 쓴다.
- 고르기: `Movable`이면 지금 `TextCopy`(바뀌지 않음, 회귀 없음). 아니면 `FontOp >= 0`(그 글 시점 글꼴을 앎)일 때 새 `TextCopyReplay`. 그것도 안 되면(글꼴 모름, Tr ≥ 4 잘림 글) 지금처럼 실패.
- 앞 글들의 글꼴·크기가 바뀌면 이동량도 그 글꼴로 계산되므로 Tf도 그대로 다시 보낸다(머리의 Tf가 쓰는 글꼴 자원도 `CollectUses`에 넣는다 — 다른 쪽에 복제할 때 `ResourceCopier`가 옮기도록).
- 머리가 너무 길면(BT 안 연산자 수 > 5000, 실제 도면의 큰 BT 블록) 실패로 둔다(제곱 비용 방지, `MaxReplayOps`와 같은 생각).

### 3.2 쓰는 곳
1. `ObjectSnippet.Extract`의 글(복제): `!s.Movable` 실패 대신 새 방법.
2. `ContentRewriter.Rewrite`의 `TransformObject` 글(옮기기·크기): 원본은 지금처럼 `HideText`. 사본은 ET 뒤에 넣는데, **그 자리의 CTM은 `EtCtm`** 이므로 `X = C·Then·EtCtm⁻¹`로 연다(지금 코드는 C⁻¹ — Movable 글은 BT 안 cm이 없어 C = EtCtm이라 같은 값). `EtOp < 0`(ET 없음)이면 실패.
3. 잘림을 물려받은 글을 옮기는 길(`RedrawOutsideClip` → `Extract(withClip: true)`)도 1을 거치므로 함께 된다.

### 3.3 화면
바뀌지 않는다. 화면은 PDFium 객체로 그린다. 저장 뒤 모양 검사(`FindChangedPages`, 화면 replay ≡ 저장)가 새 방법의 결과를 그대로 검사한다.

## 4. 설계 B — 원본 도형 스타일·원본 글자 색도 고쳐 쓰기로 (같은 막힘의 나머지)

### 4.1 원본 경로의 선·채움 (`SetShapeStyleEdit`, 원본)
- 새 `ObjectEdit`가 아니라 `TransformObject`에 선택 필드 `Style`(stroke rgb?, width, fill rgb?)을 더해 옮기기와 한 번에 접는다(같은 객체를 두 번 고치면 `edited twice` 실패가 나므로). 계획(`ContentRewritePlanner`)은 원본 번호마다 (Then, Style?, TextColor?)를 모은다. 옮기기 없이 스타일만이면 Then = 단위 행렬.
- 바이트: 경로의 `FirstOpIndex` 앞에 `q [X cm] <stroke> RG <width> w <fill> rg ` 를 넣고(경로 중간의 상태 연산자는 지금처럼 Q 뒤에 다시 적음), 칠하기 연산자를 바꾼다: 채움·선 둘 다 → `B`(원래 `f*`/`B*`/`b*` 계열이면 `B*`, 닫힘 `b`/`s` 계열이면 `b`/`b*`), 채움만 → `f`/`f*`, 선만 → `S`/`s`, 없음 → `n`. 화면(`ApplyStyle` → `SetDrawMode`)과 같은 규칙. 
  - 굵기: `ApplyStyle`은 PDFium `StrokeWidth`(객체 공간 = 그 경로의 CTM 아래 값)를 쓴다 → 바이트에도 같은 값을 그대로 `w`로(쪽 공간 배율 변환 없음). 시험으로 화면과 같은 굵기인지 확인.
  - 색: DeviceRGB(`RG`/`rg`)로 쓴다. 원래 패턴·셰이딩 채움이면 단색으로 바뀌는 것이 맞다(사용자가 고른 색).
- `ObjectCopyBuilder`가 "원본 도형 스타일 바꾸기는 사본에 옮길 수 없다"며 건너뛰는 규칙은 이번 범위 밖(그대로 둠).

### 4.2 원본 글자 색 (`SetTextColorEdit`, 원본)
- 원본을 `HideText`로 숨기고 같은 자리(Then = 단위)에 색을 덮어쓴 사본(3.1 또는 지금 `TextCopy`의 `colorOps`)을 ET 뒤에 둔다 — 지금 "글 옮기기"와 같은 모양에 색만 더함. 옮기기와 함께면 한 사본.
- 색 연산은 복제와 같은 규칙(`Tr` 1·2·5·6이면 `rg`와 `RG` 둘 다).
- 옛 글자는 파일에 보이지 않는 글자로 남는다(글 옮기기와 같음, 검색에 두 번 나오지 않게 할 필요는 없음 — 사본은 같은 글).

### 4.3 아직 막는 것 (그대로 실패, 5절 흐름으로 안내)
- 원래 글꼴 인코딩이 없는 한 줄 편집(`InsertTextLikeEdit` Encoded = null), 찾아 바꾼 글을 다시 옮기기/지우기, 글꼴 모르는 글, 잘림 글(Tr ≥ 4), 해석 불가 내용, 객체 번호 대응 실패, 암호 문서.

## 5. 설계 C — 저장 흐름: 경고 뒤 실패를 없앤다

### 5.1 예외에 종류를 단다
```csharp
public enum RegenerationFailure { LookChanged, CannotRewrite }
public sealed class ContentRegenerationException(int pageNumber, string? reason = null, RegenerationFailure kind = RegenerationFailure.CannotRewrite)
```
- `LookChanged` = 저장 결과는 만들 수 있지만 화면과 모양이 다를 수 있다 → "그래도 저장?"을 물을 수 있다. **AcceptLookChanges = true로 다시 저장하면 반드시 성공해야 한다.**
- `CannotRewrite` = 이 편집은 이 쪽에서 저장할 수 없다 → 묻지 않고 원인 안내.

### 5.2 `OutputCopyBuilder.RegenerateContent` — 고쳐 쓰기 가능 여부를 먼저 안다
- 고쳐 쓰기로 보낼 쪽이 정해질 때마다(① 시작 때 복제 쪽·강제 쪽 ② PDFium 모양 검사에 걸려 넘기는 쪽) **패처 시험 적용(`IContentRewriteProbe.CheckContentRewrites`, 파일 안 바꿈)** 을 먼저 한다. 지금 문단 쪽에만 하는 것을 모든 고쳐 쓰기 쪽으로 넓힌다(`_dry` 캐시로 실제 적용 때 다시 해석하지 않으므로 추가 비용은 시험 적용 한 번).
- 시험 적용이 거절한 쪽:
  - 복제가 있는 쪽(대안 없음) → `ContentRegenerationException(쪽, 사유, CannotRewrite)` 즉시.
  - 그 밖(PDFium 결과가 대안): `accept`면 그 쪽을 `accepted`에 넣고 경고(`LookWarning`)를 남긴 채 PDFium 결과로 저장. 아니면 `ContentRegenerationException(쪽, "PDFium changed the look; content-stream rewrite rejected: " + 사유, LookChanged)`.
- 지금 `throw` 하는 곳의 종류: 6단계 모양 검사(고쳐 쓴 결과 모양 다름) = `LookChanged`(이미 accept면 경고로 바뀜), "PDFium … and the content-stream rewrite is not available"(암호·패처 없음) = `LookChanged`(accept면 PDFium 결과로 저장 — 지금 코드 그대로), 문단 둘 다 실패 = `LookChanged`(지금 그대로), 복제 쪽 "copied objects need the content-stream rewrite …" = `CannotRewrite`.
- 패처 실제 적용(`Apply`) 단계에서 나는 예외는 시험 적용을 통과한 뒤라 원칙적으로 없다. 나면 `CannotRewrite`(기본값)로 그대로 실패 — 조용히 틀린 파일을 내지 않는다.

### 5.3 `FileWorkflow.TrySaveAsync`
- `LookChanged`일 때만 지금처럼 묻는다(문구 그대로). `CannotRewrite`면 묻지 않고 새 오류 문구 한 번:
  - `Err_Save_ObjectEditUnsupported` (ko): `{0}쪽의 객체 편집 중 이 PDF에서는 저장할 수 없는 것이 있어 저장하지 못했습니다({1}). 원본은 그대로입니다. 그 편집을 실행 취소한 뒤 저장해 주세요.`
  - (en): `Some object edits on page {0} cannot be saved in this PDF ({1}), so the file was not saved. Your original file is unchanged. Undo that edit, then save.`
  - `{1}` = 사유를 쉬운 말로(`ErrorMessages`에서 사유 문자열의 열쇠말로 고름): `text not copyable`/`text not movable`/`render mode` → "복제·이동한 글자의 구조", `clip` → "잘림이 걸린 개체", `parse`/`segment`/`object count`/`map` → "쪽 내용 구조", 그 밖 → "편집한 개체".
- `ErrorMessages.For`도 종류에 따라 두 문구 중 하나(인쇄·자동 복구 경로도 같은 문구를 받는다).
- 경고 창 문구(`AskSaveDespiteLookChangeAsync`)와 그 뒤 "모양이 다를 수 있습니다" 알림은 그대로.

### 5.4 error.log 진단 보강
저장 실패(`save`, `save-look-check`) 기록에 그 쪽의 편집 종류별 개수(예: `edits: Duplicate×3(src p1#10 Text), Transform×2`)를 한 줄 덧붙인다(`SaveService` 또는 `FileWorkflow`에서 `s.Content.For(page)` 요약). 고객 파일 없이 원인을 알 수 있게.
