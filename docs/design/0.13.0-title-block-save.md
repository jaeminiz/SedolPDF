# 0.13.0 표제란 글 고치기 — 실제 도면 진단과 저장 실패 수정 설계 (2026-11-17)

배경: "도면 표제란의 DATE·REV. NO 글자를 고칠 수 없다"는 문제를 묶음(폼) 때문으로 보고 [0.13.0-form-xobject-text.md](0.13.0-form-xobject-text.md)를 설계했다. 사용자가 실제 도면 3개(`private/TEST1~3.pdf`, 커밋 안 함, 118쪽)를 주어 **지금 앱 코드로 직접 고쳐 보고 저장**해 원인을 찾았다. 이름·내용은 적지 않고 수치만 적는다.

## 1. 진단 방법
- 시험 프로그램(저장소 밖)이 앱과 같은 부품을 그대로 부른다: `DocumentSession.OpenAsync` → `GetObjectIndex` → 텍스트 도구 hit test(글 객체 필터) → `ParagraphReader.Detect`(문단으로 잡히는지) → `TextEditPlanner.PlanReplace`(앱과 같은 카탈로그·설치 글꼴) → `ContentEditCommand` → `SaveService.SaveAsync`(앱과 같은 `PdfSharpAnnotationPatcher.Shared`) → 저장 파일을 다시 열어 새 글이 있는지 확인.
- 대상: 쪽마다 `DATE` 표제 근처(60pt 안)의 숫자 든 글 또는 날짜 꼴 글 하나. 마지막 숫자 하나를 바꿈(예: `260526`→`260527`). **쪽마다 새 세션으로 하나씩** 저장.

- 저장 실패 5건은 **모두 같은 이유**: `"Rewriting the content of page N would change its look … save blocked. Content-stream rewrite: inserting text in the original font needs the PDFium path"`.
- 표제란 글은 모두 쪽 최상위 글 객체였다(폼 안 아님 — 폼 설계 문서 10.1절).
- 이와 별도로 TEST3의 8쪽은 **글자가 선(윤곽선)으로 바뀐 도면**이라 고칠 글자 자체가 없다(텍스트 도구로 누르면 지금도 "편집 가능한 텍스트가 없습니다" 안내).

## 3. 원인 (저장 실패)
1. 텍스트 도구로 한 줄을 고치면, 새 글자가 원래 글꼴 서브셋에 다 있을 때 **원래 글꼴**(`InsertTextLikeEdit` + `DeactivateEdit`)로 계획한다.
2. 저장은 먼저 PDFium 경로(쪽 내용 다시 쓰기 `GenerateContent`)로 하고 충실도 보호로 비교한다. CAD 도면 쪽은 셰이딩·패턴·이미지 마스크·특이 색 공간 때문에 PDFium이 다시 쓰면 **모양이 달라져** 보호에 걸린다(색 정규화 2단계까지 해도).
3. 그러면 내용 스트림 직접 고쳐 쓰기(M4x, `ContentRewritePlanner`)로 넘어가는데, 이 길은 **원래 글꼴 한 줄 넣기(`InsertTextLikeEdit`)를 못 한다**(`ContentRewritePlanner.Plan`의 `case InsertTextLikeEdit: return Fail(...)`). 문단 편집의 원래 글꼴 줄(`ParagraphTextLine.Encoded`)과 찾아 바꾸기는 이 길로 쓸 수 있는데 한 줄 편집만 빠져 있다.
4. 두 길이 다 안 되어 저장이 막힌다. (`v0130-save-store` 브랜치는 이때 "그래도 저장할까요?"를 묻게 하지만, 그대로 저장하면 PDFium이 쓴 **모양이 달라진** 파일이 된다 — 근본 해결 아님.)

## 4. 수정 설계 — 한 줄 편집도 원래 글꼴을 직접 써서 저장

원칙: 문단 편집이 이미 쓰는 방식(원래 글꼴 코드북으로 계획 때 인코딩 → 저장 때 원본 글 객체의 글꼴 자원·글 상태로 직접 쓰기)을 한 줄 편집에도 쓴다. 새 개념 없음.

### 4.1 모델
`InsertTextLikeEdit`에 선택 필드를 더한다(옛 기록·시험과 호환):
```csharp
public sealed record InsertTextLikeEdit(long Id, ObjectRef Original, string Text,
    byte[]? Encoded = null, bool TwoByte = false, float Tc = 0, float Tz = 100, PdfRectF MaskRect = default) : ContentEdit(Id);
```
- `Encoded` = 원래 글꼴 코드북으로 인코딩한 글 코드. null이면 지금처럼 PDFium 경로만 가능.
- `MaskRect` = 충실도 비교에서 뺄 영역(쪽 좌표, 원래 글 경계와 새 글 예상 경계의 합집합 + 글자 크기만큼 여유). 화면의 PDFium 글 객체는 자간(Tc)·가로 비율(Tz)을 못 그리므로 문단·찾아 바꾸기와 같은 이유로 뺀다.

### 4.2 계획 (`TextEditPlanner.PlanReplace`, ① 원래 글꼴 분기)
- V14(`OriginalFontReplacer.Verify`) 통과 뒤, **코드북 인코딩을 시도**한다: `SessionFileFontSource`와 같은 방법으로 원본 파일을 PDFsharp로 열어 `PageTextFonts.Build(page, kinds)`로 그 글 객체의 글꼴 사전·보인 문자열을 얻고, `FontCodebook.TryBuild(dict, shown, learn: [(AllBytes, PDFium 글)])` → 되읽기 확인(`Decode(AllBytes)`가 PDFium 글과 같음) → `TryEncode(newText)`.
  - 공용 함수로 뺀다: `OriginalFontEncoder.TryEncode(DocumentSession s, PageId page, int originalIndex, string text) → (byte[] Bytes, bool TwoByte, float Tc, float Tz)?` (`src/PdfEditor.TextEdit/OriginalFontEncoder.cs`). `SessionFileFontSource.Build`도 내부를 이 함수의 일부로 재사용할 수 있으면 합친다(필수 아님).
  - 원본 파일을 여는 비용(큰 도면 수백 ms)이 있으므로 쪽마다 `(PageId, 쪽 버전 무관 — 원본은 안 바뀜)` 캐시. 문단 편집의 캐시가 있으면 함께 쓴다.
- 인코딩 성공 → `InsertTextLikeEdit`에 `Encoded` 등을 채운다. 실패 → 지금처럼 `Encoded = null`(PDFium 경로로만 저장 가능, 보통 쪽은 문제없음).
- 암호 문서·새 문서(파일 없음)는 인코딩하지 않는다(지금 문단 편집과 같음).

### 4.3 저장 (`ContentRewritePlanner.Plan`)
- `case InsertTextLikeEdit it when it.Encoded is not null && !it.Original.IsInserted`:
  - 원본 `it.Original.OriginalIndex`를 `textRemoved`에 넣는다(뒤따르는 `DeactivateEdit`가 끌 때 **옛 글자가 파일에서 빠지게** — 옛 날짜가 검색되지 않게).
  - 새 줄을 `Ins { Kind = 'P', Para = new ParagraphTextLine(LineId: it.Id, Text: it.Text, Placement: <원본 글 객체 행렬 — 아래>, SizePt, Color, OriginalFontSource: it.Original, Tc: it.Tc, Tz: it.Tz, JustifyExtra: 0, OrigRenderMode, it.Encoded, it.TwoByte) }`로 넣는다. 그 뒤 `TransformEdit(Inserted(it.Id))`·`DeactivateEdit(Inserted(it.Id))`는 지금 `Ins` 처리(`M`, `Disabled`)가 그대로 접는다.
  - `Placement`의 E·F = 원본 글 객체의 기준선 원점. `ParagraphLineBytes`는 2x2를 내용 스트림의 Tm×CTM에서 직접 가져오고 E·F만 `Placement`에서 쓰므로, 계획 때 `InsertTextLikeEdit`에 원점을 함께 싣는다(필드 `PdfPointF Baseline` 추가 — `PlanReplace`가 `obj.Matrix.E/F`로 채움). SizePt·Color·OrigRenderMode는 `ParagraphLineBytes`가 원본 상태 연산을 그대로 쓰므로 실제로는 쓰이지 않는다(채워만 둔다).
- `Encoded`가 null인 `InsertTextLikeEdit`는 지금처럼 `Fail`.
- 같은 원본을 다시 고친 경우(앞 줄을 끄고 새 줄): 앞 `InsertTextLikeEdit`의 줄은 `DeactivateEdit(Inserted)`로 `Disabled`가 되어 쓰이지 않는다 — 추가 처리 없음.

### 4.4 충실도 보호
- `OutputCopyBuilder.ParagraphMasks`에 `InsertTextLikeEdit`의 `MaskRect`(값이 있으면)를 더한다. 그 밖은 지금 그대로(마스크 밖이 다르면 저장 실패).

### 4.5 화면
- 바뀌지 않는다(화면은 지금처럼 PDFium `CreateTextLike`).

## 8. 손 시험 결과와 2차 수정 — 칸 간격 지키기 (2026-11-18)

### 증상 (사용자 손 시험, TEST2 7쪽)
표제란 한 줄 `N/S 190510 E.J JUNG`(SCALE·DATE·BY 세 칸)의 날짜를 고쳐 저장하니 세 칸이 한데 붙어 `N/S 191120 E.J JUNG`처럼 보였다. 글꼴은 원래 것 그대로다.

### 원인
그 줄은 글 객체 하나, `TJ` 하나다. 칸 사이는 공백 글자가 아니라 **TJ 이동값**(-3394, -1924)이고, 글자 사이에도 작은 자간 값(-13 ~ -38)이 있다:
`[<0031>-18<0012>-13<0036>-3394<0014>-14<001C>-14<0013>-34<0018>-14<0014>-34<0013>-1924<0028>…] TJ`
한 줄 편집은 **줄 전체를 새 글로 다시 쓰므로**(원래 글꼴 직접 쓰기든 PDFium 경로든) 이 이동값이 모두 사라진다. PDFium이 읽어 준 글의 공백(` `)은 이 큰 이동을 글로 흉내 낸 가짜 공백이어서, 다시 쓰면 보통 공백 폭(1차 수정의 `SpaceGap1000`)이 된다. CAD 표제란·표에서 흔한 구조라 이 문제는 이번 수정 전(PDFium 경로)에도 있었다.

### 수정 설계 — 바뀐 글자만 바꾼다
`TextEditPlanner.PlanReplace`의 원래 글꼴 분기 **앞에** "부분 바꾸기"를 둔다:
1. 옛 글(PDFium 글)과 새 글의 공통 앞부분·뒷부분을 뺀 **바뀐 구간**을 구한다(`N/S 19|0510| E.J JUNG` → `1120`).
2. 그 글 객체를 `PageGlyphWalker`로 걸어 글자(코드) 목록과 맞춘다(가짜 공백은 `GlyphInfo.Virtual`). 바뀐 구간이 **가짜 공백을 건드리지 않고**, 한 글 연산 안에 있을 때만 부분 바꾸기를 한다. 아니면 지금처럼 줄 전체.
3. 글자 수가 같고(`0510`→`1120`) 새 글자가 모두 원래 글꼴 코드북에 있으면 **코드만 제자리에서 바꾼다**: TJ 문자열 안의 그 코드 바이트만 갈아 끼우고, 이동값·자간·글 상태는 하나도 건드리지 않는다. 새 `ObjectEdit` `ReplaceCodes(ObjectIndex, [(Str, Code, NewCode)])`(ContentRewriter) — 코드 단위(1/2바이트)가 같으므로 바이트 길이도 같다. 글자 폭이 달라 생기는 차이는 새 글자 폭 − 옛 글자 폭뿐이다(숫자끼리는 보통 0).
4. 글자 수가 다르거나 코드북에 없는 글자가 있으면 찾아 바꾸기(0.4.0)의 `ReplaceTextSpanEdit`로 **바뀐 구간만** 바꾼다(나머지 글자와 칸 이동값은 그대로, 새 글은 원래 글꼴 또는 그 구간만 대체 글꼴). `ReplacePlanner`의 낱말 하나 계획을 바뀐 구간으로 불러 재사용한다.
5. 화면: `ReplaceTextSpanEdit`와 같은 방식(원래 객체를 끄고 앞·새·뒤 조각을 PDFium 글 객체로) — 3번도 이 화면 방식을 쓴다(조각 = 앞부분, 새 글, 뒷부분). 충실도 비교는 바뀐 구간 둘레만 뺀다.
6. 저장은 두 경우 모두 내용 스트림 고쳐 쓰기(찾아 바꾸기와 같음)라 그러데이션 쪽에서도 막히지 않는다.
7. 다시 고치기: 앞서 부분 바꾸기를 한 객체를 또 고치면, 그 객체의 `ReplaceTextSpanEdit`를 원래 글 기준으로 새로 계획해 바꾼다(찾아 바꾸기가 같은 글 객체를 다시 고칠 때와 같은 규칙).

### 시험
- 합성 자료: 한 TJ에 세 칸(큰 이동값 2개)과 자간이 있는 표제란 줄. 날짜만 고쳐 저장 → 세 칸 글자의 x 위치가 원래와 같음(허용 0.5pt), TJ 이동값이 그대로, 새 날짜 추출, 옛 날짜 없음.
- 글자 수가 다른 바꾸기(`N/S`→`1:10`) → 뒤 칸(DATE·BY) 위치가 그대로.
- 칸을 넘는 바꾸기(가짜 공백 포함) → 지금처럼 줄 전체(기존 동작 유지).
- 실제 자료(커밋 안 함): TEST2 7쪽 날짜 → 세 칸 위치 그대로, 1차 수정의 5쪽도 다시 확인.
