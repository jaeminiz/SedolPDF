## V22 — 찾아 바꾸기 구현 방식: 찾기

### 방법
쪽 내용 스트림(`ContentLexer`)을 처음부터 따라가며 글 상태(`Tf`·`Tc`·`Tw`·`Tz`·`Ts`·`Tr`·`Tm`·`Td`·`T*`·`'`·`"`·`q/Q/cm`)와 글꼴 폭으로 **글자마다 쪽 공간 위치**(시작점·끝점·각도·크기)를 구한다(`FindProbe.Walk`). 글꼴은 `FontCodebook`(ToUnicode + 폭)으로 풀고, 단순 글꼴에 ToUnicode가 없으면 Latin-1로 푼다. 같은 각도·같은 기준선(±0.15 글자 크기)의 글자를 위치순으로 이어 **논리 글줄**을 만들고(틈 > 0.25 em이면 가상 공백, > 1.0 em이면 줄 끊음), 그 위에서 문자열 찾기(대소문자·완전일치 — `-`·`_`·글자·숫자는 낱말 글자, `.`은 앞뒤가 글자·숫자일 때만). 찾은 글자들은 `(글 연산 번호, 문자열 순번, 글 코드 순번)`로 되돌아간다.

## V23 — 바꾸기 쓰기 충실도

### 방법 (탐침 `FindProbe.Replace`)
찾은 글자들의 글 코드를 글 연산에서 **빼고**(그 폭만큼 `TJ` 간격 숫자로 메워 뒤 글 위치 유지 — Tj 사슬·TJ 모두 `[... ] TJ`로 다시 씀) 새 글을 첫 글자 자리에 **같은 방향·크기·자간·가로 비율**로 덧붙인다(`TextLineWriter` + 첫 글자의 글 행렬; 쪽 끝에 `ContentRewriter.AppendOnly`). 새 글 인코딩은 원래 글꼴 `FontCodebook`(보인 글 코드), 비임베드 단순 글꼴은 Latin-1 직접. 안 되면 "앱 글꼴 필요"로 센다.

## V26 — 큰 도면 문단 편집 출력 사본 약 4 s

방법: A1 합성 도면(`spikes/out/bench-a1-paragraph.pdf`, 205,000 객체, 4.4 MB)을 같은 부품(`PageContent.Load`·`ContentLexer.Parse`·`ContentSegmenter.Segment`·PDFium 객체 읽기·`ObjectMap.Verify`·`ContentRewriter.Rewrite`·PdfSharp 저장·PDFium 다시 열어 렌더)으로 한 번 통과시키며 단계별 시간을 잼(웜업 1회 뒤 3회 중앙값).

| 단계 | ms |
|---|---|
| 파일 읽기 / PdfSharp 열기 | 1.5 / 1.0 |
| 쪽 내용 풀기(`PageContent.Load`) | 22 |
| `ContentLexer.Parse`(625,001 연산) | 296 |
| `ContentSegmenter.Segment` | 104 |
| PDFium 객체 종류·경계 읽기(20만 개) | 225 |
| `ObjectMap.Verify` | 15 |
| `ContentRewriter.Rewrite`(안에서 결과를 다시 파싱·분할해 검증 포함) | 814 |
| PdfSharp 쪽 내용 교체 / 저장(메모리) | 18 / 135 |
| 저장본 PDFium 다시 열기+640 px 렌더 | 538 (그 중 쪽 불러오기 140 + 전체 렌더 383, **작은 영역(160×100 px)만 렌더하면 3.8**) |
| **한 번 통과 합계** | **약 2.2 s** |

해석:
- 앱은 이 일의 일부를 여러 번 한다(M5 Task 10 기록: 객체 경계 0.2 + 시험 적용 약 1.1 + 화면 모양 기억 0.6 + 실제 쓰기 1.2 + 저장 뒤 비교 0.7 = 3.7~4.1 s). 시험 적용 결과 재사용으로 이미 0.4~0.9 s 줄였다.
- **구조 변경 없이 줄일 수 있는 것(추정):** ① `ContentRewriter` 결과 검증을 전체 재파싱 대신 바뀐 구간만 확인(최대 ‑0.4 s) ② PDFium 스레드 일(객체 읽기 0.2·화면 모양 0.6·저장 뒤 렌더 0.5)과 관리 코드 일(파싱·분할·저장)을 동시에(‑0.4~0.8 s) → **약 2.5~2.9 s**. 그래도 ≤ 2 s에 닿지 않는다.
- ≤ 2 s에 닿으려면 화면 모양 기억·저장 뒤 비교의 전체 렌더(합 약 1.1~1.3 s)를 편집 영역 주변만 렌더하도록 줄여야 한다 — 이는 **"편집하지 않은 곳이 바뀌지 않았는지" 확인하는 안전 검사를 약하게 하는 선택**이다(영역 밖 확인 포기). 사용자 결정 거리(N2).
- **판정:** 구조 변경 없이 ≤ 2 s는 어렵다 → **Task 12 취소, 0.5.0 후보로 문서화**(권고). 사용자가 N2로 "영역 검사 허용"을 고르면 별도 계획으로.

## 계획에 미치는 영향 (확정 기록은 계획서에도 적음)

1. **D9 수정 — `PageObject.Text`(TextSnapshot)로는 글자 위치를 못 구한다.** `ContentSegmenter`는 한 글 연산 뒤의 `Tm`을 모른다고 보고(글자 폭을 모름) 같은 BT 안에서 이어 쓰는 `Tj` 사슬의 스냅숏 `Tm`이 낡은 값이다. Task 4는 탐침과 같은 **새 "글자 위치 걷기"(글꼴 폭 + 글 상태 추적)** 를 만들고, `ContentSegmenter`는 객체 번호 대응(PDFium 객체와의 연결·편집 기록)용으로만 쓴다.
2. **D9 수정 — PDFium `FindAll` 교차 확인은 `-`가 든 쪼개진 낱말에서 틀린다.** PDFium 텍스트는 글 연산 끝의 하이픈을 떨어뜨린다. 교차 확인은 하이픈이 없는 낱말이나 "하이픈 제거 후 비교"로만 쓰고, 합격 기준은 합성 정답표로 한다. (부수 발견: 기존 Ctrl+F 검색도 이런 번호를 못 찾는다 — 0.4.0 범위 밖, 후보 기록.)
3. **새 글의 자리와 그리기 순서(Task 5).** 탐침은 새 글을 쪽 끝에 덧붙였지만 정식은 **원래 글 객체 `ET` 바로 뒤**(M4x `TextCopy`와 같은 자리)에 넣어 겹침 순서를 유지하고, 원래 글의 채움 색·`gs` 등 상태(`TextSnapshot.ReplayOps`)와 클립(M5 `HasOwnClip` 규칙)을 이어받아야 한다(탐침은 검정 기본 상태만 시험). `ContentRewriter`의 객체 수 검증은 "한 글 연산이 비면 글 객체 1 감소, 새 글 +1"을 알도록 확장한다.
4. **화면 모양(Task 5 시작 때 확인).** 화면은 PDFium 객체로 그리므로 글 연산의 *일부*만 바뀐 상태를 보이려면 원래 글 객체를 끄고 앞부분·새 글·뒷부분을 PDFium 글 객체 최대 3개로 다시 만든다(위치는 걷기 결과를 그대로 쓸 수 있음). 이 부분은 탐침으로 확인하지 않았다 — **검증 필요, Task 5의 첫 단계.**
5. **글꼴(D12) — 비임베드 단순 글꼴은 WinAnsi 직접 쓰기를 허용한다.** 서브셋에 없는 글자는 그 낱말만 앱 글꼴. 실제 문서에서 새 번호에 쓸 숫자 10개를 모두 가진 글꼴은 소수이므로 **대체 글꼴 빈도가 높을 것** — 미리보기의 글꼴 상태 표시가 중요하고, 코드북은 쪽이 아니라 **같은 글꼴 사전을 쓰는 문서 전체의 보인 글 코드**로 만드는 것이 낫다(쪽 단위 대비 상당히 늘어남, 위 표).

## 알려진 한계 (Task 6·이후에 반영)

1. **찾기는 열 때의 파일을 읽는다.** 같은 세션에서 이미 바꾼 낱말은 후보에서 빠지지만(편집 기록과 대조), **바꾼 새 번호는 저장하기 전에는 찾을 수 없다.** 저장 후엔 다시 찾아진다(시험으로 확인).
2. **쪽 구성이 바뀐 뒤**(쪽을 지우거나 넣음)엔 쪽 수가 달라 `FindAsync`가 `InvalidOperationException("page-structure-changed")`을 던진다(화면은 "먼저 저장하세요"류 안내가 필요 — Task 6). 쪽 순서만 바뀐 경우는 계획 단계의 객체 종류 열 대조(`PageMismatch`)로 걸러지지만, 같은 종류 열인 쪽끼리 순서가 바뀐 경우는 구분하지 못한다(검증 필요; 저장 단계의 객체 경계 대조가 마지막 안전망).
3. **길게 바꾸면** 같은 줄의 뒤 글을 덮고, 그 줄은 읽는 순서가 섞여 새 번호로 안 읽힐 수 있다 — 자동 재배치 없음(D8). `ReplaceItem.Overlap`/`ReplaceBatch.OverlapCount`로 미리보기에서 경고.
4. **화면 모양:** 화면은 PDFium 글 객체로 앞부분·새 글·뒷부분을 다시 만든다. 글자별 간격(TJ)·자간·가로 비율은 못 그리므로 그 글 객체 둘레는 저장 뒤 모양 비교에서 뺀다(`MaskRect`). 나머지 쪽은 0.1 % 블록 비교를 그대로 적용한다.
5. **바꾼 글을 나중에 지우거나 옮기면**(`DeactivateEdit`/`TransformEdit`가 원본 글 객체에 쌓임) 직접 쓰기가 거절되고 PDFium 경로로 내려가며 화면 조각이 따로 남을 수 있다 — Task 6에서 바꾼 글을 선택·삭제하는 길을 막거나 안내해야 한다(검증 필요).
