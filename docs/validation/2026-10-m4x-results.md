# M4x 검증 결과 (쪽 내용 스트림 직접 고쳐 쓰기)

계획: `docs/superpowers/plans/2026-10-21-m4x-content-stream-rewrite.md` (로컬 전용). 실제 PDF는 `private/`(커밋 안 함)의 4개 파일, 이름·내용은 적지 않고 수치만 적는다.

## Task 1 — V16: 해석기 객체 목록 ≡ PDFium 객체 목록 (2026-10-21) → **통과 (보완 규칙 2개 필요)**
- 방법: PDFsharp `ContentReader`로 쪽의 연산자 열을 읽고 객체 분할 규칙으로 종류 순서(텍스트 T·경로 P·이미지 I·셰이딩 S·폼 F)를 만들어 PDFium `GetObject(i).Type` 순서와 비교(`tests/PdfEditor.TextEdit.Tests/V16ObjectMapSpike.cs`).
- 규칙: 경로 그리기 연산(`S s f F f* B B* b b* ` — `n`은 클립 전용이라 객체 아님), 글 보이기(`Tj TJ ' "`), `Do`(리소스 `/Subtype`으로 이미지/폼), `sh`, 인라인 이미지(`BI`). **PDFium과 맞추려면 필요했던 보완 2개:** ① **빈 글(`() Tj` 등 글자가 하나도 없음)은 객체가 아니다** ② **경로는 점이 2개 이상이어야 객체**이며, 예외로 점 1개라도 **닫힌 경로(`m h`+그리기, `m s`, `m b`)는 객체**(둥근 끝 점 그리기 — 실제 PDF에서 쪽당 십수 건). 보이지 않는 글(Tr 3)·`'`·`"`·TJ는 모두 객체 하나.
- 결과: 합성 PDF 14종(문서형·도면형·색 공간/그리기 방식 12종·가장자리 사례 1종) 14/14, **실제 PDF 4개 전체 710쪽 중 706쪽(99.4 %) 종류 순서 완전 일치**, 해석 실패 0. 일치 못 한 4쪽은 모두 큰 벡터 쪽(경로 수천~4만 개)에서 객체 수가 1~34개 다름(원인 미확정 — 길이 0 경로·중복 점 등 PDFium의 폐기 규칙 추정, 검증 필요). 시험은 앞 40쪽(합성 포함 131/131)을 상시 확인한다.
- **해석:** 객체 번호 대응은 가능하다. 다만 종류 순서 일치는 필요조건일 뿐이라 계획의 Task 4(종류+경계 사각형 검증, 어긋나면 그 쪽은 새 방식 사용 불가 → 지금의 충실도 보호가 막음)는 그대로 필요하다. 0.6 %의 쪽은 그 안전망으로 처리된다.
- **참고:** PDFsharp `ContentReader`는 연산자 바이트 범위를 주지 않는다(무편집 = 바이트 동일을 보장 못 함). Task 2의 자체 어휘 분석기(바이트 범위 보존)가 필요하다 — V16은 분할 규칙만 확인했다.
- **미확인(검증 필요):** 경계 사각형 대응(CTM 추적이 필요 — Task 3·4), Type3 글꼴·텍스트 클립 모드(Tr 4~7)·폼 안 내용, `/Contents` 배열 경계에 걸친 연산자, 인라인 이미지가 실제 PDF에 거의 없어 합성 1건만 확인.

## Task 2~5 — 내용 스트림 해석기·분할기·번호 대응·재작성기 (2026-10-21) → **구현·시험 통과**

### 구성
| 파일 | 역할 |
|---|---|
| `ContentLexer` | 어휘 분석. 연산자마다 `[Start,End)` 바이트 범위(피연산자 포함) 보존, 범위 사이 틈은 공백·주석뿐 → 무편집 왕복 = 원본과 바이트 동일. 인라인 이미지는 `BI…ID…EI` 하나의 연산자(EI 뒤가 평문인지 확인). 비정상 입력은 예외 대신 `Failure`(깊이 32·피연산자 2만 상한) |
| `PageContent` | `/Contents`(배열 포함)를 줄바꿈으로 이어 붙임, Do용 XObject 종류·폼 Matrix/BBox 해석기 |
| `ContentSegmenter` | CTM·q/Q·클립 표지·BT/ET·Tm/Td/T*·`'`/`"` 상태를 따라가며 V16 규칙으로 객체 분할. 객체마다 시점 CTM, 경계 사각형(경로·그림·폼), 글 원점·글꼴 크기, 글 상태 스냅숏(복사 재현용) |
| `ObjectMap` | PDFium 객체 번호 ↔ 해석기 객체 대응 검증(개수·종류 순서·경계). 어긋나면 `Ok=false`, 인덱서가 예외 → 그 쪽은 새 방식 사용 불가 |
| `ContentRewriter` | `DisableObject`·`TransformObject`·`AppendOnly` |

### Task 4 결과 (PDFium 대조)
- 합성 14종 전부 일치. 실제 PDF 4개 전체 쪽: **696/709 쪽(98.2 %) 검증 통과** — 거절 13쪽(개수 불일치 4: V16에서 본 큰 벡터 쪽, 나머지 9: 경로 경계가 PDFium과 허용 밖으로 다름). 거절은 안전하게 "그 쪽은 새 방식 불가"가 된다. 객체 경계 비교 약 156만 개, 종류만 본 것 약 5.3만 개(폼·셰이딩·글 위치 불명·0 크기 글 상자).
- **실제 PDF로 알아낸 PDFium 경계의 성질(허용 오차 근거):** ① 줄 그은 경로 경계는 선 끝·이음 때문에 우리 계산보다 부풀며 짧고 굵은 선·뾰족한 꺾임은 선 굵기의 100배 가까이도 부푼다(그래서 줄 그은 경로는 부풀림 허용을 크게, 줄어듦은 1.5 pt + 1 %로 작게) ② 글 상자는 글자 잉크에 가깝게 작아 기준선 원점이 상자 밖일 수 있다(상자까지 거리 ≤ 2 + 1.2×글꼴 크기) ③ 폼 경계는 `/BBox` 밖으로 나가기도 한다(폼은 경계 비교 안 함, 종류·순서만) ④ 공백 글 상자는 크기 0.
- 한계: 경계 허용이 넓은 부분(굵은 줄 경로의 부풀림, 폼, 셰이딩)은 종류·순서와 다른 객체들의 경계 일치가 안전망이다. 번호가 한두 개 밀리면 종류 순서나 그 뒤 객체 경계에서 걸러진다고 보지만, "같은 종류 두 개가 서로 바뀐 경우"는 경계가 비슷하면 놓칠 수 있다(검증 필요 — 실제로는 같은 분할 규칙이라 발생 근거는 못 찾음).

### Task 5 결과 (재작성)
- 끄기: 경로 → 칠하기/선 연산자를 `n`으로(경로의 `W` 클립은 그대로), 글 → `3 Tr (…) Tj <원래 Tr> Tr`로 감싸 글자 폭·뒤 글 위치 유지(Tr 4~7 클립 모드는 거절), 이미지·폼·셰이딩·인라인 이미지 → 연산자 제거.
- 옮기기·크기: `q X cm <객체 연산> Q`, **X = C·Then·C⁻¹**(C = 객체 시점 CTM). 경로는 첫 `m/re`부터 칠하기까지를 감싼다. 시험에서 회전 쪽·y 뒤집힘(CAD 식)·기울임 중첩 CTM·이동+크기 합성이 모두 정확(경계 오차 < 1e-4). 글은 BT 안에서 q/cm을 쓸 수 없으므로 **원본을 `3 Tr`로 숨기고 ET 뒤에 `q X cm` + 글 상태·색 재현 + `BT Tm 보이기 ET Q` 사본을 그린다**(원점이 정확히 `Then`만큼 이동).
- 안전 검사: 결과를 다시 해석해 q/Q·BT/ET 균형 프로필이 원본과 같은지, 종류별 객체 수가 기대(끈 것 −, 글 사본 +)와 같은지 확인. 거절: 특이 CTM, 클립을 같이 하는 경로, 경로 중간의 상태 연산자, 글 위치를 모르는 글(앞 글 뒤), BT 안 cm/q/Q, 클립 렌더 모드, 번호 범위 밖·같은 객체 두 번 편집.
- 덧붙임: 원본이 q/BT를 열어 둔 채 끝나면 앞에 `q`를 두고 끝에서 모두 닫은 뒤 `q … Q`로 붙인다.
- 실제 PDF 전체(709쪽)에서 무작위 끄기·옮기기 6개씩: 연산자 범위 이어 붙이기 = 원본 **0건 불일치**, 재작성 **성공 702·거절 7(모두 "글 위치 불명")·결함 0**.

### 한계·미확인 (검증 필요)
- **렌더 충실도는 Task 8에서 확인한다.** 이 Task들은 텍스트/기하 수준(다시 해석한 결과)만 검증했다 — PDFium으로 그려 편집 외 부분 0 %인지는 미확인.
- 글 옮기기는 같은 BT 안의 뒤 글에 영향이 없도록 사본 방식을 택했으므로, 옮긴 글은 쪽에서 맨 뒤(해당 BT 직후)에 그려져 겹침 순서가 바뀔 수 있다. 글 위치를 모르는 글(앞 글 바로 뒤, Tm/Td 없이 이어진 Tj)은 옮길 수 없다(끄기는 가능).
- 옮기기는 선 굵기·점선 무늬도 `cm`과 함께 변환된다(키우면 선도 굵어짐). 폼 안 객체·Type3·Tr 4~7은 범위 밖.
- 새 객체 직렬화(Task 6)·패치 단계 통합(Task 7)은 아직. `ContentRewriter.Rewrite`의 `appends`는 호출 계약만 만들었다.
