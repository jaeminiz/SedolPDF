## Task 1 — 검증 V12~V15 (2026-10-19)

### V12 — 쪽을 불러올 때마다 다시 적용(replay)하는 방식이 성립하는가 → **통과**
- 갓 불러온 쪽에서 ① 이미지 끄기(`FPDFPageObj_SetIsActive(false)`) ② 사각형 옮기기(`SetMatrix`) ③ 원래 글꼴로 새 텍스트 객체(`FPDFTextObj_GetFont` → `FPDFPageObj_CreateTextObj` → `FPDFText_SetText` → `FPDFPage_InsertObjectAtIndex`)를 하면 렌더가 바뀌고, **그 쪽으로 새로 만든 텍스트 페이지(검색)에 새 글이 나온다**.
- `GenerateContent` 없이 쪽을 닫았다가 10번 다시 불러와도 객체 수·순서·종류가 원래와 같고 렌더도 원래와 같다(차이 0 %) → 원본 번호가 고정된다(결정 C2 성립).
- 사본에서 같은 편집 + `GenerateContent` + 저장 → 다시 열면 새 글이 있고, 끈 이미지는 파일에 없다(객체 종류 `1,1,3,2,2,1` → `1,1,1,2,2,1`).

### V14 — 원래 글꼴로 바꾼 글자를 어떻게 확인하는가 → **규칙 확정, 거짓 통과 0**
**규칙:** 원래 글꼴로 새 텍스트 객체를 만든 뒤 ① `FPDFText_SetText` 성공 ② `FPDFTextObj_GetText` 되읽기가 입력과 **완전히 같음** ③ 공백이 아닌 글자 수가 입력과 같고, 그 객체만 렌더했을 때 글자 칸(텍스트 페이지의 글자 상자)마다 잉크가 있음 — 셋 다 맞아야 원래 글꼴을 쓴다. 하나라도 틀리면 그 줄은 앱 글꼴(Noto Sans KR)로 바꾼다(결정 C4).

| 원래 줄의 글꼴 | 바꿀 글 | 되읽기 | 잉크 | 판정 |
|---|---|---|---|---|
| Arial 서브셋(TrueType) | 원래 글자만 `Arial 321 CBA` | 같음 | 11/11 | 원래 글꼴 사용 |
| Arial 서브셋 | 없는 글자 섞임 `Zebra Quiz 789` | `era i ` (없는 글자가 빠짐) | — | 앱 글꼴로 |
| 맑은 고딕 서브셋(CID, Identity-H) | 원래 글자만 `다나가 검토` | 같음 | 5/5 | 원래 글꼴 사용 |
| 맑은 고딕 서브셋 | 없는 한글 `라마바 검토` | ` 검토` | — | 앱 글꼴로 |
| Helvetica(표준 글꼴, 임베드 없음) | `Zebra Quiz 789` | 같음 | 12/12 | 원래 글꼴 사용 |
| 맑은 고딕, **`/ToUnicode` 없음** | 원래 글자만 / 없는 글자 | 둘 다 빈 글 | — | 둘 다 앱 글꼴로 |

- 서브셋에 없는 글자는 PDFium이 조용히 빼 버리므로(되읽기에서 사라짐) 되읽기 비교가 핵심이다. 잉크 검사는 되읽기는 맞는데 글리프가 비어 있는 경우를 막는 보조 검사다.
- `/ToUnicode`가 없는 글꼴은 PDFium이 유니코드 → 글자 코드를 고르지 못해 원래 글자만 써도 실패한다. 기술 검증 S3에서 한글 도면의 텍스트가 cmap으로 판정되지 않았던 것과 같은 경향으로, **실제 한글 도면에서는 대부분 앱 글꼴로 바뀔 것**으로 예상한다(검증 필요: 실제 도면 줄 단위 비율은 Task 10에서 잼).

### V15 — 폼(묶음) XObject 안 객체를 편집할 수 있는가 → **안 됨**
- 바깥 폼의 자식에 `SetIsActive(false)`·`SetMatrix`는 호출이 성공(1)하지만, 쪽에서 `GenerateContent` → 저장 → 다시 열면 **자식 수(3)와 위치가 그대로**다(텍스트 왼쪽 20.48 pt, 200 pt 옮긴 것이 사라짐). `FPDFPage_GenerateContent`는 쪽 내용 스트림만 다시 쓰고 폼의 스트림은 다시 쓰지 않는다.
- 따라서 **결정 C10은 "폼 전체를 한 객체로"(옮기기·크기·지우기만)** 로 간다. 폼 안 텍스트를 고르면 "묶음 안에 있어 편집할 수 없습니다"를 알린다. CAD 도면은 그림 전체가 폼 하나로 묶인 경우가 많아 사용자 결정 U1을 여쭌다(추천: 폼 전체만 — M4 범위 유지. "묶음 풀기"는 별도 작업).

### 사용자 결정 U1 (2026-10-20)
- **폼(묶음) 안 객체는 폼 전체만 편집**(옮기기·크기·지우기). "묶음 풀기"는 넣지 않는다. (추천안 확정)

## Task 8 — 텍스트 편집·텍스트 추가 화면 (2026-10-20)
- **텍스트 편집 도구:** 글자 객체(또는 앱 글꼴로 넣은 줄)를 한 번 누르면 그 자리에 한 줄 편집 창(원래 글 채움). Enter = 확정, Esc = 취소, **한글 IME 조합 중인 글자가 있으면 Enter·Esc는 조합을 끝내는 키라 무시**(M3b 답글 칸과 같은 판정). 글이 그대로면 아무것도 하지 않음. 확정하면 `TextEditPlanner.PlanReplace`(원래 글꼴 → 앱 글꼴 → 거절 이유)를 전용 스레드에서 세우고 `ContentEditCommand` 하나로 실행(실행 취소 한 번).
- **안내:** 앱 글꼴로 바뀌면 화면 아래에 짧게 "원래 글꼴에 없는 글자가 있어 기본 글꼴로 바꿨습니다."(2초), 바꿀 수 없으면 이유(암호 문서·글꼴 파일 없음·기본 글꼴에도 없는 글자)를 대화상자로. 쪽에 편집할 글이 하나도 없으면 "편집 가능한 텍스트가 없습니다…"(C11), **묶음(폼) 위를 누르면 "묶음 안에 있어 편집할 수 없습니다…"**(C10·V15).
- **텍스트 추가 도구:** 쪽을 누르면 그 자리(글자 상자의 왼쪽 위)에 편집 창 → 확정하면 앱 글꼴 12pt 검정 한 줄(`InsertAppTextEdit`). 빈 글이면 만들지 않음. **회전된 쪽에서는 글이 바로 서게 돌려 넣음**(`ObjectToolController.TextPlacement`, 4/10 버그 리포트와 같은 규칙). 암호 문서에서는 도구가 꺼지고 툴팁에 이유.
- 시험(`TextEditInputTests` 10개, 헤드리스 합성 입력): Enter 확정·Esc 취소, 글이 그대로면 편집 없음, IME 조합 중 Enter·Esc 무시(조합 끝난 뒤 Enter가 확정), 앱 글꼴 알림, 글 없는 쪽 안내, 이미지 위 클릭은 안내 없음, 폼 위 클릭 안내, 새 텍스트 만들기·실행 취소, 빈 글은 만들지 않음, 암호 문서에서 새 텍스트 도구 꺼짐·툴팁.
- **검증 필요(실제 입력):** 실제 마우스 클릭으로 편집 창이 열리는 위치·크기, **실제 한글 IME**(조합 중 Enter·Esc는 `PreeditText`를 직접 설정해 흉내 낸 시험만 함), 편집 창의 바깥 클릭 확정(Popup 가벼운 닫기), 125/150% 배율.

## Task 9 — 이미지·도형 넣기, 편집 탭·홈 탭 연결, 객체 속성 (2026-10-20)
- **편집 탭:** 5개 자리 표시 단추를 실제 동작으로 연결. 묶음 "편집": 텍스트 편집 · 개체 편집 · 텍스트 추가 · 이미지 추가, 묶음 "도형 넣기": 사각형 · 타원 · 선(작은 메뉴 대신 단추 3개로 폈다 — 도형 종류가 하나의 도구 켜짐 표시와 겹치지 않게, 편집 탭 단추 8개). 홈 탭 "편집" 묶음의 4개도 같은 명령(자리 표시 문구 `Msg_ComingInM4M5`는 리본에서 사라짐). **쪽 수정 권한이 없는 문서에서는 모두 꺼지고 툴팁에 이유**, 암호 문서에서는 텍스트 추가만 꺼짐. 도구 종류 `ToolKind.AddEllipse`·`AddLine` 추가(`AddShape` = 사각형).
- **이미지 추가:** 파일 고르기(PNG·JPEG, 25 MB 넘으면 읽지 않고 검증 실패로) → **지금 보는 쪽 가운데**에 쪽 폭의 절반(높이는 80%) 안으로 비율 유지해 넣음 → 바로 객체 편집 도구로 선택된 상태. 형식·크기 검사는 문서 자산 보관소(PNG·JPEG, 50 메가픽셀 등 M3a 상한) — 안 되면 "이 이미지를 넣을 수 없습니다…" 안내 후 아무것도 바꾸지 않음. 회전된 쪽에서는 바로 서 보이게 돌려 넣음.
- **자산 연결(`session.Assets`):** 쪽 객체 이미지는 replay가 `DocumentSession.Assets`에서 읽는데 이 값은 지금까지 아무도 앱 공용 보관소(`AppearanceServices.Assets`)로 연결하지 않았다 → 탭을 만들 때 연결(화면 replay·저장·복구·인쇄가 같은 보관소를 봄, 공용 보관소는 PNG·JPEG 검증기를 가짐).
- **도형 추가:** 끌어서 그림(끄는 동안은 점선 미리보기), 놓으면 `InsertShapeEdit`. 사각형·타원은 어느 한 변이 3pt 미만, 선은 길이가 3pt 미만이면 만들지 않음(M2 도형 도구의 최소 크기 규칙과 같은 취지). 기본 스타일 선 #E5372D 1.5pt, 채우기 없음. 끄는 동안 도구가 바뀌면 만들지 않음.
- **객체 속성 패널(오른쪽 패널, 객체를 고르면 주석 속성 대신 보임):** 위치·크기(mm, 소수 1자리, 쪽 좌표 기준 왼쪽·아래) — 바꾸면 옛 경계 → 새 경계 행렬 하나(`TransformEdit`). **새로 넣은 도형:** 선 색·두께·채우기(M2 견본 10색 + 없음) → `SetShapeStyleEdit`. **새로 넣은 텍스트(앱 글꼴 줄):** 글자 크기·색 → 같은 글을 새 크기·색으로 다시 넣고 옛 줄을 끔(한 명령, 새 줄이 선택을 이어받음; 이를 위해 `TextEditPlanner.PlanReplace`에 크기·색 덮어쓰기 매개변수를 추가). 계획서의 `SetTextStyle` 편집 종류는 만들지 않고 이 방식으로 대신함.
- 시험(`AddToolsTests` 14개 + `ObjectPropertiesPanelTests` 1개 + 리본 시험 2개 수정): 편집 탭 단추 활성·도구 선택·체크 표시, 권한 없는 문서에서 모두 꺼짐·툴팁, 홈 탭 묶음이 실제 명령, 이미지 쪽 가운데·선택·실행 취소, 파일 고르기 명령(취소 포함), 이미지가 아닌 파일 거절, 회전된 쪽의 이미지·텍스트 배치 계산, 도형 최소 크기·타원 끌기·실행 취소·사각형과 선, 속성 값·스타일 변경이 명령 하나·위치 크기 변경 행렬·앱 글꼴 줄 크기 변경, 속성 패널이 만들어짐.

### V13 충실도 확대 — **이전 V13 결론이 틀렸다**
- **V13의 "GenerateContent 후 0 %"는 사실상 의미가 없었다.** 쪽에서 바뀐 객체가 없으면 PDFium은 내용을 사실상 다시 쓰지 않는다(편집 없이 `GenerateContent`만 하면 실제 PDF 4개가 0 px 차이). **객체를 하나라도 바꾸면 쪽 전체를 다시 쓰고**, 그때 다음이 틀어진다. 합성 샘플(제작 프로그램·색 공간별 12종)과 실제 PDF 4개 앞 3쪽으로 확인했다.

| 그리기 방식 | 객체 하나 편집 후 저장 | 비고 |
|---|---|---|
| 셰이딩(`sh`) 객체 | **사라짐** (27 % 픽셀 다름) | 도면의 그러데이션 |
| 패턴 색(타일링·셰이딩 패턴 채우기/선, 글자 포함) | **사라지거나 회색으로 변함** | |
| 이미지 마스크(스텐실)의 채우기 색 | **검정으로 변함** (10 %) | |
| ICCBased·CalRGB·Separation·CMYK·Gray 도형·글 색 | 색 정규화 없이는 **다른 색**(검은 배경까지) | 정규화(`NormalizeColors`)로 해결 |
| 알파·혼합 모드, 글자 그리기 방식(채움+선, 선), 폼 안 ICC | 정상 (정규화 후 0 %) | |
| **글 객체 색 다시 지정(정규화)** | 실제 PDF에서 **글자 간격이 있는 글이 깨짐**(글자가 겹쳐 읽을 수 없음) | **직전 수정(NormalizeColors)이 만든 회귀** |
| CMYK 글·도형 | RGB 근사로 **색이 조금 달라짐** | 허용(차이 작음) |

- **직전 수정의 회귀:** 2026-10-20에 넣은 `NormalizeColors`는 모든 글·도형의 색을 다시 지정해 PDFium이 쪽의 글을 전부 다시 쓰게 만든다. 실제 PDF(Word 계열 2개)에서 글자 간격(Tc/Tw)이 있는 줄이 **겹쳐 깨지는** 것을 확인했다(앱 화면은 정상, 저장 파일만 문제).
- **조치 — 충실도 보호(`OutputCopyBuilder.RegenerateContent`):** 편집을 적용한 쪽의 모양(메모리)을 기억하고, 다시 쓴 파일을 열어 비교한다(8×8 블록: 평균색이 크게 다르거나 "잉크" 픽셀 수가 크게 다르면 다른 블록, 전체 블록의 0.1 % 초과면 실패). **쪽마다 가장 덜 건드리는 방식**으로 시도한다: ① 색을 건드리지 않음 → ② 도형 색 정규화 → ③ 도형·글 색 정규화. 모두 다르면 조용히 망가진 파일을 내지 않고 `ContentRegenerationException`으로 저장·인쇄를 멈춘다(문구: "N쪽에는 … 저장하지 못했습니다. 원본은 그대로입니다. 이 쪽의 객체 편집을 실행 취소한 뒤 저장해 주세요"). 편집을 실행 취소하면 다시 저장된다.
- 시험 `ColorSpaceFidelityTests`(합성 12종: 정상이면 0 %·알려진 한계 5종은 반드시 막힘), `RealPdfGuardTests`(저장소에 없는 `private/`가 있을 때만, 어느 쪽이 막히는지 임시 폴더에 보고), `IccColorOutputTests`(Quartz 흰 배경). 합성 샘플 `CreateDrawingLike`의 그러데이션은 편집 샘플(`m4-objects-drawing.pdf`)에서 끔(`gradient: false`).
- **알려진 한계(중요, 사용자 영향):**
  1. 셰이딩·패턴 채우기·이미지 마스크가 있는 쪽은 **객체 편집 후 저장이 막힌다**(편집한 쪽만, 다른 쪽은 무관). CAD 도면의 해치(패턴)·그러데이션에서 부딪힐 수 있다.
  2. 실제 PDF 4개(앞 3쪽 × 객체 하나 제자리 편집) 중 **3개는 통과, 1개(한글 매뉴얼 PDF)는 한 쪽이 막힘**(글자가 겹쳐 깨지는 줄 — 정규화 없이도 PDFium이 다시 쓰면 틀어지는 줄이 있음). 이 비율은 실제 사용 PDF에서 더 높거나 낮을 수 있다(검증 필요).
  3. 근본 해결은 PDFium `GenerateContent`에 기대지 않고 쪽 내용 스트림을 직접(PDFsharp) 고쳐 쓰는 것 — M4 설계(replay + GenerateContent)의 바꿈이라 **사용자 결정 필요**(후속 작업 제안).
  4. 확인하지 못한 것: Type3 글꼴, 인라인 이미지, 소프트 마스크(`SMask`), 4쪽 이후, 다른 뷰어. 작은 이미지 마스크(8×8 블록 미만)는 보호가 못 잡는다.
- 비용: 편집한 쪽이 있으면 저장마다 메모리 렌더(긴 변 640 px) 쪽당 1회 + 다시 열기 1회가 더 든다(통과하면 추가 저장 없음, 막히면 최대 2회 더 씀).
